# 신뢰도 검증 데이터셋

기존 평가(`eval/run_eval.py`, 회의 3건)는 고친 뒤 같은 데이터로 다시 재서 100%가 일반화 근거가 되지 못한다.
이 데이터셋은 처음 보는 회의에서 **얼마나 자동으로 처리하고, 자동 처리한 것은 얼마나 맞고, 사람에게 넘긴 것은 정말 넘길 만했는지**를 잰다.

## 시험 셋 원칙

- 개발 셋(1~5주)만 보고 코드·프롬프트를 고친다.
- **시험 셋(6~10주)은 마지막 측정에만 쓴다.** 시험 셋 결과·전사문을 보고 코드를 고치지 않는다. 고쳤다면 그 결과는 시험 셋 수치로 발표하지 않는다.
- 시험 셋 실행 시점은 메인 작업에서 정한다. 실행 기록은 `results_test.md`에 남는다.

## 규모

| | 개발 셋 | 시험 셋 | 합계 |
|---|---|---|---|
| 회의 | 20 | 20 | 40 |
| 정답 결정 | 100 | 100 | 200 |
| 할 일 | 50 | 50 | 100 |
| 의견 | 30 | 30 | 60 |
| 질문 | 100 | 100 | 200 |
| └ '찾지 못함' 함정 | 20 | 20 | 40 |

프로젝트 4개(OPS 기존 + 경비 정산 EXP · 현장 점검 앱 FLD · 영업 대시보드 SLS)가 10주 동안 매주 회의한다. 회사 정책은 시연 데이터 R4 v3에 조항 4개(SEC-04·SEC-05·FIN-01·DATA-01)를 더했다.
인물·회사·프로젝트는 모두 가상이며, 권한 위반·규정 위반 발언은 데이터셋에서 새로 만든 가상 인물만 한다.

## 폴더

```
AUTHORING.md     작성 기준 (정답 스키마, 충돌 판단 기준, 현상 목록)
dataset.py       세계 합치기 · 정답 읽기 · 원장 시뮬레이션 · 검사 (--check)
run.py           평가 러너
review_sample.py 사람 검수 표본 (docs/reliability_review.md)
world/           data/project에 덧붙는 프로젝트·인물·주제·정책·예외·기준 문서·원장 시드
meetings/        회의 전사문 40건
gold/            프로젝트별 정답 (결정·할 일·미결·함정, 의견, 질문)
results_dev.*    개발 셋 결과
```

## 실행

```bash
.venv/bin/python eval/reliability/dataset.py --check
pgrep -fl "run_eval|reliability/run.py|process_meetings"   # 다른 평가가 돌면 끝난 뒤 실행 (응답 시간 오염)
.venv/bin/python eval/reliability/run.py --split dev
.venv/bin/python eval/reliability/run.py --split dev --only questions --resume   # 중간에 멈췄으면 이어서
.venv/bin/python eval/reliability/run.py --split dev --rescore                   # 실행 없이 다시 채점
```

- 격리: 코드와 `data/project`를 임시 폴더로 복사하고 데이터셋 세계를 합친 뒤 돌린다. 원장·벡터 DB는 임시 `LEDGER_STORE`. 시연 `store/`는 건드리지 않는다.
- 기본 세계 임베딩은 `.cache/`에 두고 재사용한다(입력이 바뀌면 다시 만든다). 원자료는 `.cache/raw_<split>.json`.
- 모델: 로컬 qwen3:8b (분류·작성 모두). 유료 API 없음.

## 측정 방식

회의를 날짜순으로 열고, 회의마다 ① 전사문을 검색 색인에 넣고 ② 회의 정리를 돌리고 ③ 팀장이 정답대로 검토했다고 보고 원장을 갱신하고 ④ 그 시점의 의견·질문을 돌린다.
원장은 매 시점 정답 기준이라 앞 회의의 추출 오류가 뒤 질문 채점에 번지지 않는다(항목별 독립 채점). 실제 운영의 누적 오류는 이 수치에 들어가지 않는다.
미래 회의 전사문은 그 시점 검색에 나오지 않는다. 열람 권한(사용자별)은 이 평가에서 끈다.

| 지표 | 정의 |
|---|---|
| 결정 정밀도·재현율 | 예측의 확정 발언 번호가 정답 근거 발언(제안·확정)에 들면 같은 결정 (1:1) |
| 할 일 담당·기한 정확 | 정답 할 일 기준. 원문에 없는 담당·기한은 비워야 정답 |
| 충돌·변경 탐지율 | 정답의 막는 충돌(정책·권한·기존 결정·기준 문서)·기준 변경·승인 대기 확정 중 같은 근거 ID로 짚은 비율 |
| 충돌 오탐 | 충돌이 없어야 할 결정에 막는 충돌을 붙인 비율 |
| 의견 판정 정확 | conflict / allowed_with_waiver / no_conflict / needs_approval 일치 |
| 질문 정답률 | 확정은 결정 ID나 핵심어, 승인 대기는 상태와 ID, 미결·찾지 못함은 상태 표현 |
| 자동 처리율 | 결정 라벨이 '확인 필요'가 아님 · 의견 판정이 needs_approval이 아님 · 질문 답 라벨이 '확인 필요'가 아님 |
| 자동 처리 정확도 | 자동 처리한 것 중 맞은 비율 |
| 넘긴 것 중 애매·오류 | 사람에게 넘긴 것 중 실제로 충돌·애매했거나 시스템 출력이 틀렸던 비율 (넘길 만했나) |
| 응답 시간 | 회의·의견·질문별 중앙값·상위 5% |

비율마다 95% 신뢰구간(Wilson)과 표본 수를 함께 적는다.

## 사람 검수

정답은 시나리오와 함께 설계했지만 사람 검수 전이다. `docs/reliability_review.md`의 표본(분할별 20%)과 검수 필요 목록을 확인한 뒤 수치를 확정한다.
