# 개발 셋 기준선 오류 분석

대상: `results_dev_baseline.json` (코드 de0a8d7, 용어 색인 전). 저장된 결과만 읽었고 모델은 다시 부르지 않았다.
분류: **(a)** 채점·정답지 문제 / **(b)** 데이터셋 세계가 시스템에 안 들어감 / **(c)** 파이프라인 약점.

## 결론

- 낮은 수치의 대부분은 **(c) 파이프라인 약점**이다. (b)는 없었고, (a)는 채점 규칙 3가지를 고쳐 다시 채점했다(아래 표).
- 기존 소규모 평가(회의 3건)가 100%였던 것은 규칙(확정 표현 목록, 권한표 주제 연결표, 기한 표현)과 프롬프트가 그 3건에 맞춰져 있었기 때문이다. 처음 보는 회의에서는 같은 규칙이 다음처럼 깨진다.
  1. **gate의 '까지' 규칙** — 기한이 아닌 '3번까지 재시도', '10장까지', '전화 호출까지'도 할 일 배정으로 보고 결정에서 뺀다. 놓친 결정 22건 중 12건.
  2. **진행자 발언 무조건 인정** — PM·PL의 질문·안내·보류('다음 주에 다시 보죠')까지 결정으로 통과. 틀린 결정 72건 중 진행 발언 29건 + 보류 발언 12건.
  3. **주제 고르기** — 주제 목록이 22개 → 49개로 늘자 맞힌 결정의 주제 정확이 45%. 주제가 틀리면 '주제 불확실'로 넘기거나(47건, 넘긴 결정의 58%) 비교할 기존 결정·조항을 못 찾는다.
  4. **질문 경로** — '~했죠?', '~해 봐도 될까요?' 같은 말투가 잡담·질문으로 빠진다. 질문 15건, 의견 10건이 엉뚱한 경로.
  5. **근거 질문의 후보** — 주제로 찾은 결정의 '승인 대기' 건이 질문과 무관해도 답에 '아직 승인 대기'를 쓰게 강제된다(validate 규칙). 질문 오답 10건.
  6. **프로젝트 범위** — 화면에서 프로젝트를 골라도 다른 프로젝트 결정으로 답한다. 질문 오답 6건.

## 고칠 곳 후보 (개발 셋 기준, 우선순위)

0. 회의 추출이 해석 실패로 비면 '결정 없음'이 아니라 오류로 드러내기 (EXP-M04: 결정 5·할 일·미결이 통째로 사라짐).

1. gate 할 일 판별: '까지'를 날짜·요일 앞에서만 기한으로 보기 (결정 놓침 12건, 충돌 놓침 상당수).
2. 진행자 단정 인정 범위: 질문·안내·보류 표현이면 진행자라도 결정 아님 (틀린 결정 41건).
3. 의견·질문 경로 규칙: '~해도 될까요/되죠/괜찮나요', '~하기로 했죠?' (경로 오분류 25건).
4. 근거 질문: 승인 대기 언급 강제를 '고른 후보가 승인 대기일 때'로 좁히기, 화면에서 고른 프로젝트 밖 결정은 참고로만.
5. 권한표 주제 연결표를 주제 목록과 함께 관리 (새 주제가 늘면 기술 선택으로 떨어짐), 금액·기간 기준값 비교.

이 목록은 개발 셋에서만 나왔다. 고친 뒤에도 시험 셋은 한 번만 잰다.
