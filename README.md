# meeting-decision-ledger — 회의 요약 · 결정 정리 비서

회의 전사문에서 **결정과 할 일을 근거 발언과 함께** 뽑고, 그 결정이 과거 결정·프로젝트 기준 문서·사내 정책과 충돌하는지 확인한 뒤, **사람이 승인한 결정만 원장(ledger)에 남기는** AI Agent. 나중에 "그건 왜 그렇게 정했지?"에 원장 → 원문 발언까지 거슬러 올라가 답한다.

SKALA AI Capstone 미니 프로젝트 · 과제 2(신규 AI 서비스). 강사 배포 `all_total_vue_student`의 구조(LangGraph 노드, MCP stdio, FastAPI·SSE, Vue 화면, SQLite 세션, 의존성 주입)를 재사용했다.

![회의 정리 화면](docs/images/m04_report.jpg)

## 1. 주제 선정 배경

강의 녹음을 Whisper로 전사해 정리하면서 용어 오인식("버니게이트" → 권위 게이트)과 환각 문장이 100곳 넘게 나왔다. 사내 회의도 같은 문제를 겪는데, 더 큰 문제는 **회의에서 정한 것이 제대로 기록되지 않고, 나중에 뒤집혀도 아무도 모른다**는 점이다. 회의록 정리를 "요약"이 아니라 "결정 관리"로 바꾸면 RAG·MCP·멀티 에이전트·권위 게이트를 모두 의미 있게 쓸 수 있다고 봤다.

## 2. 해결하려는 문제

가상 프로젝트(SKALA "운영 장애 대응 AI Agent", 회의 OPS-M01~OPS-M05)에 실제로 자주 생기는 상황을 넣었다.

| 상황 | 회의 | 놓치면 생기는 일 |
|---|---|---|
| SSE로 정한 뒤, PM 불참 회의에서 WebSocket으로 다시 바꾸자고 함 | OPS-M04 | 과거 결정·아키텍처 원칙 위반을 아무도 모름 |
| PL 혼자 운영 반영을 2주 연기 | OPS-M04 | 2주 이상 지연은 본부장 승인 사항 (권한 위반) |
| "보안 예외 받은 게 있으니" 운영 로그 원문을 외부 LLM에 | OPS-M04 | 예외는 마스킹 샘플 한정 — 범위 밖 |
| 구 정책(MySQL 표준)을 근거로 MySQL 결정 | OPS-M05 | 현행 정책은 PostgreSQL. 구버전 근거 |
| "예전에 롱폴링에서 SSE로 바꾸고 나서…" 회상 발언 | OPS-M04 | 결정으로 오인하거나 대체된 결정과 비교해 오탐 |
| 담당자 없는 할 일, 기한 없는 할 일 | OPS-M05 | 아무도 안 함 |

LLM 단독이나 단순 RAG로는 이 상황을 놓치거나, 이미 대체된 결정을 현재 기준으로 잘못 들어 오탐한다 (8절 실측).

## 4. 시스템 아키텍처

```
브라우저(Vue) ──SSE──▶ FastAPI(server.py) ──▶ LangGraph(agent/ledger_graph.py)
                                                  │  MCP stdio
                                                  ▼
                                   mcp_ledger_server.py ──▶ SQLite 원장·정책 (진실의 원천)
                                                        └─▶ Chroma R1·R2·R3·R4 (검색 색인)
```

### 4.1 RAG 4종과 우선순위

| | 담는 것 | 성격 | 권위 |
|---|---|---|---|
| R1 회의 원문 | 누가 언제 무슨 말을 했나 | 기록(증거), 고치지 않음 | 인용 근거로만 |
| R2 기준 문서 | 지금 무엇을 하기로 되어 있나 | 현재 상태, 버전 관리 | 결정 없는 주제의 기본값 |
| R3 결정 원장 | 언제·누가·무엇을·왜·무엇 대신 | 변경 이력, 승인 후 추가만 | 결정된 주제에서 R2보다 우선 |
| R4 거버넌스 | 사내 정책·아키텍처 원칙·결정 권한표 | 상위 규칙, 버전 관리 | 최상위 제약 |

**R4 > R3(유효 결정) > R2(현행 버전) > R1(근거 전용).** 이 해석은 LLM이 아니라 코드(`resolve_current`)가 한다. 대체된 결정·구버전은 판정 단계에 들어가지 않는다. 정책 예외(waiver)는 범위·만료일과 함께 별도 표에 두고 정책 자체를 바꾸지 않는다.

**검색 결과를 그대로 믿지 않는다 — "모르면 모른다"를 코드로 보장**

| 장치 | 무엇을 막나 | 기준 |
|---|---|---|
| 주제 하한 | 목록에 없는 새 주제에 가장 가까운 기존 주제를 억지로 붙이는 것 (조용한 폴백) | 1위 점수 0.50 미만이면 주제 없음 |
| 원문 하한 | 논의한 적 없는 주제에 무관한 발언을 "관련 논의"로 붙이는 것 | 0.58 미만 발언은 버림 → "찾지 못함" |
| 주제 두 경로 대조 | LLM이 고른 주제가 문장과 안 맞는데 그 주제의 결정과 비교하는 것 | 그 주제의 기존 자료와 0.50 미만이면 '주제 불확실' |
| 다른 주제 유사 결정 | 주제를 잘못 골라 진짜 관련 결정을 놓치는 것 | 다른 주제 유효 결정이 0.55 이상이고 고른 주제보다 가까우면 경고 |
| 결정 ID 직접 조회 | "OPS-0007은 왜?"처럼 ID로 묻는 질문 (벡터 검색은 기호에 약함) | 문장의 ID를 원장에서 바로 꺼냄 |

주제가 불확실하거나 다른 주제의 유사 결정이 있으면, 결정·기준 문서 비교 결과로 '충돌'이나 '문제없음'을 단정하지 않고 **확인 필요**로 사람에게 넘긴다. 정책 충돌은 문장 유사도로 찾은 것이라 그대로 둔다.
**근거 질문은 후보를 넓게 모으고 LLM은 ID만 고른다.** 결정 상위 12건과 프로젝트의 미결을 후보로 보여 주고, LLM이 질문에 실제로 답하는 데 필요한 ID만 고른다("해당 없음" 가능). LLM은 문장을 쓰지 않고, 후보에 없는 ID는 버린다. 고른 결과가 주제로 찾은 결과와 다른 결정을 가리키면 확인 필요. 프로젝트당 결정·미결이 수십~수백 건인 지금 규모에서는 예상 질문을 미리 만들어 색인하는 것보다 정확하고 관리할 것이 없다 ([설계안 §4](docs/설계_재구성안.md)).

**날짜·참석자·결정자·승인자는 RAG를 쓰지 않는다.** 회의 목록·원장·이력 표를 코드가 조회한다(사실 질문 경로).

기준값은 `eval/retrieval_eval.py`로 정답·함정 문장의 점수 분포를 재서 정했다([결과](eval/retrieval_results.md)): 주제는 정답 최소 0.553·함정 최대 0.463, 원문은 관련 발언 최소 0.626·함정 최대 0.527. 값은 `ledger/thresholds.py` 한곳에 있다.

### 4.2 처리 흐름 — 베이스와 같은 노드

```
route ─┬ chat ───────────────────────────────────────────────── chat_answer
       ├ schedule (이번 주·지난주·10월 회의 등) ─────────────── schedule_answer (LLM 없이 회의 목록 + 추가된 일정으로)
       ├ schedule_add (다음 주 화요일 3시 회의 잡아줘 등) ─────── schedule_add (초안만. 저장은 화면 '추가' → POST /events)
       ├ fact (언제 회의? 참석자? 누가 승인?) ──────────────────── fact_answer (LLM 없이 회의 목록·원장·이력 표 조회)
       └ meeting / interview / opinion / question
            → plan → gate → research ⇄ replan_check → analysis → write ⇄ validate → finalize
```

| 노드 | 베이스(장애 진단) | 이 프로젝트 |
|---|---|---|
| route | chat / 파이프라인 분기 | 회의·면접·의견·질의·일정 조회·일정 추가·잡담 (분명하면 규칙, 애매하면 LLM). 추가 동사(추가·잡아·등록·넣어·만들어)나 시각이 날짜와 함께 있으면 일정 추가, 묻는 문장은 조회 |
| schedule_add | — | 날짜·시간은 코드가 해석(상대 주는 조회와 같은 규칙), LLM은 제목·참석자·프로젝트만 → 원문·users.json·projects.json 대조. 겹침·권한을 붙여 초안만 만든다 |
| plan | MCP Prompt + 태스크 분해 | MCP Prompt·Resource로 절차를 받고, 결정 후보는 코드가 표시 → LLM이 분류·요약. 확정 표현이 있는데 분류되지 않은 후보는 한 번 더 묻는다(누락 재확인) |
| gate | analysis 태스크 코드 제거 | 결정이 아닌 것(회상·보류) 제거, 인용·담당자·기한을 원문 대조로 확정 |
| fact_answer | — | 날짜·참석자·결정자·승인자·승인 요청·대체될 결정을 표에서 조회. '이거'는 직전 답이 가리킨 결정·회의(대화방에 저장)로 코드가 풀고, 없으면 되묻는다 |
| research | 병렬 조회 + 재시도 | 결정마다 현재 기준·권한·예외 조회 (MCP Tool, 병렬, 실패 격리). 질의는 후보를 넓게 모아(결정 12건 + 미결) **LLM이 관련 ID만 고르고**, 주제로 찾은 결과와 다르면 확인 필요 |
| replan_check | 런북 없으면 재조사 | 기준이 없으면 R1 원문 논의 추가 조회 (1회) |
| analysis | 비교 분석 | LLM은 기준마다 같음/다름만 → **코드 판정표**가 충돌 종류 결정. 이어서 보강(`agent/enrich.py`): 상태 라벨, 해결 제안(권한표 기준값 숫자 비교·예외 범위·대체 결정 + 'AI 제안' 대안), 칸 기록(대상·변경·범위·조건, 근거에 없는 값은 비움), 근거 번호 달린 요약, 미결 주제, 회의 인사이트 |
| write | 고품질 모델 답변 | 보고서는 템플릿, 질의 답변만 LLM 토큰 스트리밍 |
| validate | 길이 검사 → 재작성 | 코드 검사(인용 글자 일치, 결정 ID 표기) 뒤 질의 답변은 LLM 심판이 관련성·근거·완전성·명확성 1~5점, 3점 미만이면 재작성. 최대 3회 |
| finalize | 최종 답변 | 회의 기록(결정 후보·미결·할 일·요약)을 저장하고 같은 사안의 앞선 미결을 이번 결정에 잇는다. 문제없는 결정은 승인 대기로 원장 등록. **승인은 사람만** |

LLM과 코드의 역할: **LLM은 요약·분류·"같은가 다른가"만, 무엇이 근거인지·지금 유효한 기준이 무엇인지·충돌 종류는 코드가 정한다.**

### 4.4 화면 구성, 역할, 번호 체계

사내 포털 배치에 그룹웨어 남색을 썼다. 왼쪽 위는 대화방(최신순), 왼쪽 아래는 로그인한 사용자와 설정, 오른쪽 위는 알림과 메뉴, 오른쪽 아래는 버전.

| 영역 | 동작 |
|---|---|
| 대화방 목록 | 최신순. 메뉴에서 프로젝트를 고르면 그 프로젝트 대화가 위로 미끄러져 올라오고(재정렬 애니메이션) 나머지는 흐려진다. 메뉴를 닫거나 선택을 풀면 최신순으로 돌아온다 |
| 메뉴 | 회의 캘린더(월 이동) + 프로젝트 목록. 프로젝트를 누르면 다른 프로젝트 회의는 캘린더에서 흐려지고, 그 프로젝트 원장이 나온다 |
| 알림 | 승인 요청·승인·반려·열람 결과. 팀장에게는 "승인했습니다", 요청자에게는 "승인되었습니다/반려되었습니다" |
| 관리자 콘솔 (팀장) | 결정·의견 승인과 반려, 승인 뒤 '확인'에서 열람 범위 설정, 열람 요청 승인(이 사람만 / 같은 역할 전체 / 7일), 회의별 역할 접근 권한, 처리 이력 |
| 설정 | 사용자 전환, RAG 저장소 4종 건수와 검색(현행만 / 대체·구버전 포함), 프로젝트·번호 규칙 |

| 역할 | 사용자 | 권한 |
|---|---|---|
| 팀장 | 정한결 | 모든 회의 열람, 결정·의견·열람 승인, 관리자 콘솔, 일정 추가 |
| 담당자 | 서지후 | 참석 회의 열람, 원문이 파기된 과거 결정 열람, 승인 요청, 일정 추가 |
| 팀원 | 장상민·노영오·김태림·한소율·황민채 | 참석 회의 열람, 승인·열람 요청, 일정 추가 |
| 인턴 | 윤하린 | 참석 회의만, 그 외는 열람 요청. 일정은 본인만 참석하는 것만 추가하고, 다른 사람이 들어간 일정은 저장 대신 팀장에게 요청 알림 |

일정 추가는 팀원 이상이면 바로 저장한다(사람이 화면에서 '추가'를 누른 뒤). 일정은 결정처럼 이후 판단의 근거가 되지 않고 고치기 쉬워서 팀장 승인을 두지 않았다. 대신 다른 사람의 시간을 잡는 일이라 저장되면 참석자에게 알림이 가고, 인턴이 남의 일정을 넣으려 하면 팀장에게 요청으로 넘어간다.

승인 대상은 세 가지다. 회의 전사문 정리 자체는 기록이라 승인하지 않는다.

| 승인 대상 | 내용 | 승인자 |
|---|---|---|
| 회의에서 나온 결정 | 정리 중 문제없음·기준 변경으로 판정된 결정을 승인 대기로 원장에 올림. 승인 전에는 근거로 쓰지 않음 | 팀장 |
| 의견 → 결정 | 의견 검토 결과를 결정으로 올려 달라는 요청 | 팀장 |
| 열람 요청 | 권한 밖 회의·결정 열람 (이 사람만 / 같은 역할 전체 / 7일) | 팀장 |

사규 위반·권한 밖 결정·기존 결정과 모순된 결정은 승인 대상으로 올리지 않고 '충돌'로 표시만 한다. 2주 이상 지연(본부장), WebSocket(아키텍처 위원회), 원문 외부 전송(보안 담당)처럼 팀장 혼자 승인할 수 없는 사안이기 때문이다. 권한자가 기존 기준을 바꾼 결정(PM의 응답 기준 60초 변경)은 위반이 아니라 '기준 변경 — 문서 개정 필요'로 올라간다.

사용자와 회의 등장인물은 모두 시연용이다. 위반 장면(권한 밖 결정, 면접 금지 질문)은 가상 인물 서지후가 맡는다.

열람 기본값은 **그 회의 참석자만**이다. 권한 없는 결정이 질문의 근거가 되면 그래프가 그 결정의 내용을 LLM에 넘기지 않고 "열람 권한 없음"으로만 표시한다.

번호 체계는 프로젝트 약자 + 일련번호다. 약자는 `data/project/projects.json`에서 프로젝트를 만들 때 정한다.

| 대상 | 형식 | 예 |
|---|---|---|
| 결정 | 약자-4자리 | OPS-0012, CSB-0004 |
| 회의 | 약자-M2자리 | OPS-M04 (입력할 때는 M04도 됨) |
| 면접 | 약자-I2자리 | HBE-I01 |
| 추가된 일정 | EVT-4자리 | EVT-0001 |
| 정책·예외 | 영역-2자리 / W-3자리 | SEC-01, W-001 |

### 4.5 기술 요소와 강의 내용 연결

| 요소 | 강의에서 다룬 원칙 | 이 프로젝트 |
|---|---|---|
| Multi-Agent | 계획·역할 분리·체크 노드 (Supervisor 흐름) | 단일 StateGraph 안의 역할 노드형: plan(추출)·research(조회)·analysis(판정)·write(작성)·validate(검증)가 역할별 프롬프트·모델로 분리 |
| MCP | Tool은 부를 때마다 달라지는 것, Resource는 거의 안 바뀌는 것, Prompt는 표준 절차 | 원장 검색·해석은 Tool, 정책 조항·기준 문서·주제 목록은 Resource, 추출·판정·면접 절차는 Prompt |
| 권위 게이트 | LLM 판단을 그대로 믿지 말고 코드로 강제 | gate, 판정표, 권한 검사 |
| Validator | 심사 후 재작성, 횟수 상한 | validate 최대 3회, 질의 답변은 LLM-as-Judge 점수까지. 끝내 근거 대조에 실패하면 원장 기록으로 만든 답으로 교체 |
| 재시도 | 일시 오류만 재시도 | `with_retry` (timeout만) |
| 병렬·격리 | gather + 동시 실행 상한 + 부분 결과 | `gather_safe` (Semaphore 2, return_exceptions) |
| 모델 티어링 | 작업별 모델 분리 | `fast_llm`/`quality_llm`/`chat_llm`, 입력창 모델 조합(자동·정확·빠름·가장 빠름), 조합별 그래프 미리 생성 |
| SSE | 단방향 스트림은 SSE | `/chat/stream`, 토큰 스트리밍 |
| 세션·캐시 | 상태는 외부 저장소, 비용 절감 | SQLite `session.db`, 같은 요청 재사용(원장·정책·원문 지문이 같을 때) |
| 의존성 주입 | 숨은 의존 제거, 테스트 가능 | `LedgerDeps` + partial, 가짜 LLM·MCP 테스트 |
| HITL | 되돌리기 어려운 행동 전 사람 승인 | 원장 승인 버튼 |
| LangSmith | 노드별 trace | `@traceable`로 노드·LLM·MCP 호출을 연결. OPS-M04 한 번에 노드 43·MCP 도구 18·LLM 7개 기록 (7.4) |

## 5. 주요 구현 기능

| 기능 | 내용 |
|---|---|
| 회의 전사문 정리 | 회의 정보(날짜·참석자), 근거 번호 달린 요약, 결정마다 **상태 라벨**(확인 필요·승인 대기와 이유)·근거 인용·충돌·**해결 방향**, 할 일(확인 필요 결정에 묶이면 경고), 미결, **눈여겨볼 점**(팀장 불참·같은 사안 반복 변경·이전 미결 해소). 결과는 회의 기록에 저장 |
| 회의 기록·사안 | 회의 목록(원문을 파기해도 남음)·회의에서 나온 항목·사안(같은 주제를 회의를 가로질러 묶음)·이력 표. 앞 회의의 미결이 뒤 회의 결정으로 이어짐 |
| 사실 질문 | "이거 언제 회의고 참석자 누구야?", "누가 승인했어?"를 LLM 없이 표 조회로. '이거'는 직전 답의 대상 |
| 추가 의견 검토 | 의견이 유효 결정·사내 정책·기준 문서와 충돌하는지. 결과: 충돌 / 예외 범위 안에서 가능 / 기준 변경 / 문제없음. 결정으로 올려 달라는 승인 요청 버튼 |
| 근거 질의 | **[확정]·[승인 대기]·[미결]·[확인 필요]·[찾지 못함]** 라벨 + 1~2문장 답 + 결정 기록 블록(결정 번호·시행일·결정자·이유·기각한 대안·원문 인용) + 이전 논의 + **사안의 흐름**. 원문이 파기된 과거 결정은 원장 인용으로 |
| 일정 질문 | "이번 주 회의 몇 개야?"를 LLM 없이 회의 목록과 추가된 일정으로 답함 (지난주·지지난주·N주 전·10월 등, 회의·면접·기타 일정 구분) |
| 일정 추가 | "다음 주 화요일 오후 3시 OPS 주간 회의 잡아줘"를 초안 카드로. 날짜·시간은 코드가 해석(오늘·내일·모레, 이번·다음·다다음 주 X요일, M월 D일, 오전·오후 N시 반, HH:MM~HH:MM, N분·N시간), 모르는 값은 빈칸으로 두고 되물음. 같은 참석자의 겹치는 회의·일정 경고. '추가'를 눌러야 저장, 취소 가능. 일정 달력·미니 달력에 표시. 저장소는 `CalendarProvider`(로컬 SQLite 기본, 구글 팀 달력은 연결 준비만 — [docs/calendar_integration.md](docs/calendar_integration.md)) |
| 면접 전사문 정리 | 질문 요약·답변 요약 쌍, 공정성 점검(직무 무관 개인정보 질문, 면접 중 합격 확정). 점수·합격 여부는 내지 않음 |
| 승인·권한 (HITL) | 결정·의견 승인과 반려는 팀장만. 승인함에 원문 인용과 **승인하면 대체될 결정** 미리보기, 승인 전 문장·주제 **수정**. **미결함**: 열린 미결의 경과일·후속 할 일, 기한이 지나면 확인 필요 표시, 사람이 닫기. 열람 요청 승인 범위(이 사람만·같은 역할·전체)와 기간(1회·프로젝트 기간·무기한·직접 입력). 승인·반려 알림 |
| 범위·모델 선택 | 입력창 아래 프로젝트·회의(날짜 달력) 지정, 입력창 안 모델 조합(자동·정확·빠름·가장 빠름) |
| 같은 요청 재사용 | 같은 회의 정리·질문은 원장·정책·문서·원문이 그대로면 저장된 답을 돌려줌. 추가 요청·"다시 만들기"는 새로 처리 |
| 사내 포털 화면 | 대화방(최신순·관련순), 회의 캘린더·프로젝트 원장, 관리자 콘솔, 설정(RAG 저장소 조회·번호 규칙) |

## 6. 실행 방법 (Mac)

```bash
bash sh/setup_venv.sh
```

```bash
cp .env.example .env
```

```bash
ollama pull qwen3:8b && ollama pull qwen3:0.6b && ollama pull qwen3-embedding:4b
```

```bash
.venv/bin/python scripts/ingest.py
```

```bash
bash sh/run.sh
```

브라우저에서 http://127.0.0.1:8100 — 로그인할 사용자를 고르고 예시 버튼을 누르거나 직접 입력한다. 왼쪽 아래 전환 버튼으로 사용자를 바꾼다.

시연 상태로 되돌리기 (서버를 끈 뒤):

```bash
bash scripts/reset_demo.sh
```

원장·RAG를 시드로 되돌리고, 시연용 대화방 9개와 승인 대기·열람 요청 각 1건을 넣는다. **시연용 대화 내용은 실제 실행 결과를 옮겨 적은 하드코딩 목업**(`scripts/seed_demo.py`)이다. 실제 결과는 화면에서 새로 질문하면 나온다.

Ollama가 느린 맥북은 `.env`에 `LLM_BACKEND=openai`와 본인 `OPENAI_API_KEY`를 넣으면 OpenAI(gpt-4o-mini)로 실행된다. 과금되며, 임베딩은 계속 로컬 Ollama를 쓴다. 실측 수치는 로컬 qwen3:8b 기준이다.

일정 저장소는 `.env`의 `CALENDAR_PROVIDER`로 고른다. `local`(기본)은 `store/calendar.db`에 저장한다. `google`은 연결 준비만 된 상태라 저장하지 않고 보낼 요청을 로그로만 남긴다(dry-run). 실제 연결 절차는 [docs/calendar_integration.md](docs/calendar_integration.md).

서버 없이 터미널에서 한 번 돌려 보기:

```bash
.venv/bin/python scripts/run_graph.py "OPS-M04 회의 정리해줘"
```

| 의견 검토 | `마스킹한 로그 샘플 100건으로 외부 모델 품질 비교를 해 보면 어떨까요?` | 예외 범위 안에서 가능 — W-001 |
| 의견 검토 | `운영 로그 원문을 외부 Claude API로 보내서 요약하면 어떨까요?` | 충돌 — SEC-01, OPS-0004 (예외는 마스킹 샘플 한정) |
| 근거 질의 | `SSE는 왜 골랐어?` | OPS-0007, 2026-09-29, 서지후, 이유·기각 대안 + OPS-M02 원문 인용 |
| 근거 질의 | `예전 고객센터 챗봇에서는 왜 웹소켓을 그만뒀어요?` | CSB-0004 — 원문이 파기돼 원장 인용으로 답함 |
| 근거 질의 | `캐시는 어떻게 하기로 했어?` | 논의는 있었지만 결정되지 않음 + 원문 논의 인용 |
| 승인(HITL) | 원장 표에서 OPS-0012(60초) 승인 | OPS-0005가 "대체됨 → OPS-0012"로 바뀌고, 이후 `응답 시간 기준이 지금 몇 초예요?`에 60초(OPS-0012)로 답함 |

| 일정 질문 | `지난주 일정은 몇개야` | "지난주(10-12~10-18) 일정은 3건입니다 (회의 1건, 면접 2건)" + 목록, LLM 호출 0회 |

## 8. Before / After 실측

같은 입력(회의 OPS-M03~OPS-M05, 추가 의견 5건, 근거 질의 6건)을 세 방식으로 돌렸다. 모두 로컬 qwen3:8b (think off, temperature 0). 정답지는 직접 만든 결정 11·의견 5·질의 6건이고, 틀린 사례를 고친 뒤 같은 데이터로 다시 쟀다.

- **Before-A LLM 단독**: 회의록·질문만 주고 한 번에 답하게 함
- **Before-B 단순 RAG**: 4종 자료를 버전·대체 구분 없이 검색해 붙여 줌 (흔한 RAG 구성)
- **After**: 이 그래프

| 지표 | Before-A LLM 단독 | Before-B 단순 RAG | After 결정 원장 |
|---|---|---|---|
| 결정 재현율(%) | 91 | 82 | 100 |
| 결정 정밀도(%) | 77 | 53 | 100 |
| 회상 발언 오추출(건) | 0 | 1 | 0 |
| 인용 원문 일치(%) | 92 | 94 | 100 |
| 할 일 담당·기한 정확(%) | 11 | 11 | 100 |
| 충돌 탐지율(%) | 0 | 88 | 100 |
| 충돌 오탐(건) | 0 | 2 | 0 |
| 의견 판정 정확(%) | 20 | 80 | 100 |
| 대체된 결정 인용(건) | 0 | 2 | 0 |
| 근거 질의 정답(%) | 0 | 50 | 100 |
| 평균 처리 시간(초) | 8.5 | 14.2 | 23.5 |
| LLM 호출 수 | 14 | 14 | 63 |
| 토큰 | 5389 | 12181 | 40706 |
| 비용 환산(USD, gpt-4o-mini 단가) | 0.0016 | 0.0037 | 0.0122 |

- 단순 RAG는 충돌을 잡지만 **대체된 결정을 근거로 들고 오탐**한다. 우선순위·필터가 이를 없앤다
- LLM 단독은 사내 정책·과거 결정을 모르니 충돌 탐지 0. 할 일 기한 연도를 2023으로 지어냈다
- 결정 재현율 91→100: 직전 측정에서 놓친 OPS-M03 [5] PL의 단정 발언('그건 버니게이트로 코드에서 걸러요')을 **누락 재확인**(확정 표현이 있는데 분류되지 않은 발언만 한 번 더 묻기)이 잡았다
- 100%는 직접 만든 정답지(결정 11건·의견 5건·질의 6건) 기준이다. 표본이 작아 일반화된 성능이 아니다
- 대가: 처리 시간 LLM 단독의 약 2.8배(23.5초 대 8.5초), LLM 호출 4.5배(63회 대 14회). 회의 정리에 칸 기록·근거 달린 요약·해결 방향 대안·미결 주제 호출이, 질의에 후보 선택 호출이 더해졌다. 판정 지표는 이전과 같다
- 비용: 같은 토큰을 gpt-4o-mini 단가($0.3/1M)로 환산하면 회의 3건·의견 5건·질의 6건 전체가 약 1.2센트

측정: 회의 기록·해결 제안·사실 질문·후보 선택을 넣은 뒤(1163347 이후) 기준. 판정 지표는 40bdc99와 같고, 처리 시간·호출이 늘었다. 기존 결정이 없는 새 주제의 결정은 "문제없음" 대신 "비교할 기준 없음"으로 표시된다

재실행: `.venv/bin/python eval/run_eval.py` (결과 `eval/results.md`, 원본 출력 `eval/results.json`)

## 9. 개발 중 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| 추출 응답이 10분 넘게 안 끝남 | 작은 모델이 같은 항목을 끝없이 반복 | 출력 상한 `num_predict`, 컨텍스트 `num_ctx` 16k 명시 (기본 4096이면 프롬프트가 잘림) |
| 충돌 목록에 ARC-02가 10번, OPS-0007은 누락 | LLM에게 충돌 목록을 직접 쓰게 함 | LLM은 기준별 same/different만, 분류는 코드 판정표 ([ADR-05](docs/adr.md)) |
| 근거 인용에 회의 전체 발언이 붙음 | LLM이 근거 번호를 넓게 고름 | 근거 = 제안 발언(3발언 이내) + 확정 발언으로 코드가 제한 |
| "그렇게 진행하죠" 결정 누락, "아직 확정은 아닙니다"를 결정으로 | LLM 단독 판별 | 확정 표현·보류 표현 규칙으로 후보 표시 후 LLM 분류 |
| 할 일 기한이 2023년, 없는 담당자 생성 | 모델이 연도·이름을 지어냄 | 회의 연도로 보정, 원문에 없는 이름·날짜는 비움 |
| 마스킹 샘플 의견을 충돌로 판정 | 예외 범위를 다른 판단과 섞어 물음 | 예외 범위는 별도 한 문항으로 질문 |
| 과거 프로젝트 질문에 현재 결정으로 답함 | 질문 대상 프로젝트를 구분 안 함 | 주제 선택 때 프로젝트도 고르게 하고 그 프로젝트 결정을 먼저 제시 |
| 논의한 적 없는 주제에도 "논의는 있었지만 결정되지 않음" | 원문 검색에 유사도 하한이 없어 가장 가까운 발언이 붙음 | 점수 분포를 재서 하한 0.58, 미달이면 "찾지 못함"으로 답하게 검증 |
| 주제를 못 정하면 검색 1위 주제를 점수와 상관없이 붙임 | 조용한 폴백 | 하한 0.50, 미달이면 새 주제. LLM 주제와 검색이 어긋나면 '확인 필요' |
| LLM 판정 출력이 깨지면 '문제없음' | 빈 판정을 판정표가 '충돌 없음'으로 읽음 | 파싱 실패·빈 판정은 '확인 필요'. 기준이 없으면 '비교할 기준 없음'으로 따로 표시 |
| 답변에 근거에 없는 숫자 | 3번 다시 써도 틀리면 모델 문장을 그대로 냄 | 날짜·숫자·ID를 근거와 글자 대조, 3번째에도 틀리면 원장 기록으로 만든 답으로 교체 |
| 충돌만 찾고 "그래서 어떻게"는 사람 몫 (검사기에 머묾) | 판정 뒤 단계가 없음 | 해결 방향: 권한표 기준값을 숫자로 비교해 승인자 안내(2주 ≥ 2주 → 본부장, 줄이면 PM), 같은 조항의 예외와 범위, 승인하면 대체될 결정과 그 결정의 기각 대안, 'AI 제안' 대안(금지된 방식을 되풀이하면 코드가 버림) |
| 미결·할 일·요약이 보고서로만 나가고 사라짐, 다음 회의와 안 이어짐 | 회의 기록 저장 없음 | 회의 목록·항목·사안·이력 표. 같은 사안의 앞선 미결을 다음 회의 결정에 잇고 '이전 미결 해소'로 표시 |
| "누가 승인했어?"를 결정 근거 질의로 처리 | 사실 질문 경로 없음 | 사실 질문은 표 조회로(LLM 없음), '이거'는 직전 답의 대상으로 |
| 요약이 확인 필요인 결정을 '결정됨'으로 씀 | 요약을 LLM이 자유롭게 씀 | 줄마다 근거 번호, 근거 없는 줄 삭제, 확인 필요 결정 줄엔 상태 표시, 방향 줄은 코드가 집계 |
| 할 일 경고가 낱말 하나만 겹친 엉뚱한 결정에 붙음 | 첫 일치에 연결 | 가장 많이 겹치는 결정 하나, 2등과 동점이면 잇지 않음 |
| 기준 조회가 실패해도 '문제없음'으로 승인 대기 등록 | 조회 실패를 '기준 없음'과 같은 값으로 채움 | 실패 표시를 남기고 판정 없이 '승인 필요'로 사람에게 돌림 (테스트 추가) |
| 없는 회의 ID에서 500 오류 | 원문 없이 gate로 진행 | plan 뒤 조건 분기로 바로 안내문 작성 (테스트 추가) |
| 회의 1건 처리 55~64초 | 회의 전체 발언을 매번 LLM에 보냄, 출력이 김 | 후보 발언과 앞 2발언만 보내고, 용어집은 등장한 오인식만, 요약 25자·판정 사유 20자로 제한 → OPS-M04 55→50초, OPS-M05 64→42초 |
| 회의 정리 뒤 입력창이 사라짐 | 긴 보고서가 flex 자식의 기본 최소 높이 때문에 화면 밖으로 본문을 늘림 | 본문·스크롤 영역에 `min-height: 0` |
| 답변이 나오는 동안 스크롤이 잠김 | 토큰마다 맨 아래로 강제 이동 | 바닥 근처에 있을 때만 따라 내려가게 변경 |
| 캘린더 서랍에 스크롤바가 생기며 칸이 밀림 | 스크롤바가 폭을 차지 | `scrollbar-gutter: stable`, 칸 폭 `minmax(0, 1fr)` |
| LLM 단독 채점이 0%로 나옴 | 모델이 발언 번호 대신 목록 순번을 씀 | 인용문 위치로 발언 번호를 찾아 공정하게 채점 |

## 10. 한계와 향후 개선

선택별 트레이드오프는 [docs/adr.md](docs/adr.md).

- **평가 데이터와 정답셋을 직접 만들었고**, 틀린 사례를 보고 고친 뒤 같은 데이터로 다시 쟀다. After의 100%는 "설계한 함정을 모두 처리한다"는 뜻이지 일반화 성능이 아니다 → 실제 회의록·다른 사람이 만든 정답셋으로 검증 필요
- 결정 후보 규칙(확정 표현·진행자 발언)이 한국어 회의 말투에 의존한다
- 주제 키가 틀리면 엉뚱한 기준과 비교한다. 두 경로 대조로 의심스러우면 사람에게 넘기고 승인 화면에서 고칠 수 있지만, LLM과 검색이 같이 틀리면 못 잡는다. 주제 목록은 수동 관리
- 미결 → 결정 연결은 같은 프로젝트·주제에서만 한다. 미결에 주제를 못 붙이면 잇지 않는다(억지 연결 방지). 회의 밖에서 정해진 것은 미결함에서 사람이 닫아야 한다
- 'AI 제안' 대안은 근거가 없는 새 생각이라 검토가 필요하다 (숫자를 지어내거나 충돌한 방식을 되풀이하면 코드가 버린다)
- 회의 정리에 칸 기록·요약·대안 호출이 더해져 회의 1건이 60~80초로 늘었다 (정확성을 우선한 선택)
- 검색 하한(0.50·0.58)은 30문장·18질의의 작은 자체 평가셋으로 정했고, 같은 셋으로 확인했다. 데이터가 바뀌면 다시 재야 한다
- 권한 검사는 "결정자 또는 참석자 중 권한자"로 본다. 권한자가 참석만 하고 동의하지 않은 경우를 구분하지 못한다
- 예외 범위 판단("마스킹 샘플")은 LLM에 의존
- 처리 시간: 의견·질의를 포함한 평균은 23.5초로 LLM 단독(8.5초)의 약 2.8배. 회의 1건 정리는 60~80초(로컬 8B). 실행마다 2초 안팎 편차(10-21 재실행 25.4초), 판정 지표의 반복 측정은 아직
- 사람 승인이 병목이 될 수 있다. 승인함에 원문 인용과 대체될 결정을 같이 보여 판단 시간을 줄인다
- 화자 분리는 입력에 있다고 가정 (Whisper 단독으로는 화자 구분이 안 됨)
- 하드코딩: 프로젝트·사용자 목록(`data/project/*.json`), 주제→권한표 매핑(`AUTH_TOPIC`), 확정 표현·금지 질문 정규식, 시연용 대화 목업(`scripts/seed_demo.py`)
- 회의 요약은 발언 앞 40자만 보고 쓰므로 세부 맥락을 놓칠 수 있다
- 로그인은 시연용(비밀번호 없음). 실제 사내 도입 시 SSO 연동 필요
- 계획 대비 변경: 진행 계획의 'LLM 심판 2단 검증'은 코드 검증 + 답변 품질 심판으로, 'LangSmith Dataset 비교'는 자체 평가 스크립트(`eval/run_eval.py`)로 대신했다
- 모듈화: 그래프 노드 11개가 `agent/ledger_graph.py` 한 파일에 있다. 노드별 파일 분리는 제출 직전 회귀 위험 때문에 하지 않았다
- 향후: LLM-as-Judge를 회의 요약 보고서까지 확대, LangSmith Dataset 연동, 회의 녹음 → 화자 분리 → 원장까지 이어지는 입력 파이프라인

### 면접 전사문 정리

전사문 정리의 한 종류로 면접 전사문도 받는다(R1 면접 전사문, R4 공정성 규칙 FAIR-01·FAIR-03). 결과는 질문 요약·답변 요약 쌍과 공정성 점검(직무와 무관한 개인정보 질문, 면접 중 합격 확정)이다. FAIR-01은 채용절차법 제4조의3 취지를 옮겼다. 점수·합격 여부는 내지 않는다. 면접 전체를 다루는 별도 에이전트는 이 프로젝트와 다른 방향의 후속 과제로 둔다.
