## 1. 진행 사항 소개

### 1.1 선택한 과제
과제 2 신규 프로젝트. Base AI Agent(운영 인시던트 대응)의 노드 구조·의존성 주입·MCP·LangSmith 틀은 그대로 두고, 주제를 **회의에서 정한 것을 관리하는 에이전트**로 바꿨다. 강의 녹음을 Whisper로 전사해 정리하다가, 요약보다 "그래서 뭘 정했고 그게 예전 결정과 맞는지"를 찾는 데 시간이 더 든다는 것에서 출발했다.

### 1.2 해결하려는 문제 — 회의가 끝나면 사람이 하는 일 5가지
| # | 일 | 지금 하는 방식 | 이 에이전트 |
|---|---|---|---|
| 1 | 정리 | 회의록을 읽고 누가 뭘 정했는지, 할 일은 누구에게 갔는지 골라냄 | 결정·할 일(담당·기한)·미결을 발언 번호와 함께 추출 |
| 2 | 비교 | 지난 결정·프로젝트 기준·사내 규정을 뒤져 바뀐 점과 부딪히는 점을 정리 | 4종 기준과 자동 비교, 승인 권한자·예외 범위로 해결 방향까지 |
| 3 | 근거 | 몇 주 뒤 "왜 그렇게 정했어?"가 오면 원문을 처음부터 다시 읽음 | 확정·승인 대기·미결·확인 필요·찾지 못함 라벨과 원문 인용 |
| 4 | 제안자 | 이 아이디어를 누가 처음 냈는지 찾아 다시 물어봄 | "누가 제안했어?" → 근거 발언의 화자를 모델 없이 0.2초에 |
| 5 | 보안 | 회의 내용이 기밀이라 외부 LLM에 맡기기 어려움 | 전부 로컬 모델(qwen3:8b), 외부 전송 없음 |

가상 프로젝트(운영 장애 대응 AI) 회의 OPS-M04에서는 PM이 빠진 사이 이미 정한 SSE를 WebSocket으로 다시 결정하고, PL 혼자 운영 반영을 2주 미뤘다(2주 이상은 본부장 승인 사항). 아무도 몰랐다. LLM에 회의록만 주면 사내 규정을 몰라 못 잡고, 흔한 RAG는 이미 대체된 옛 결정을 근거로 엉뚱한 충돌을 낸다.

### 2.2 파이프라인 — 모델은 고르기만, 판정은 코드, 확정은 사람
```
분류 → 찾기 → 판정 → (애매하면 '확인 필요'로 보류) → 팀장 승인
```
- **분류(route)** — 규칙이 먼저 가르고, 규칙에 안 걸릴 때만 모델이 고른다. 사실 질문은 모델을 거치지 않아 0.2초.
- **찾기(research)** — 결정마다 MCP 도구로 규정·기준 문서·예외·권한표·원문을 모은다. 부족하면 한 번 더 찾는다(replan, 1회 상한).
- **판정(analysis)** — 충돌·권한 위반·승인된 변경을 가리고, 권한표 기준값·예외 범위·대체될 결정으로 해결 방향을 낸다.
- **보류** — 판정 실패, 비교할 기준 없음, 검증자 이의, 주제가 애매함 → 단정하지 않고 '확인 필요'로 사람에게.

신뢰도를 올리는 검사 네 곳:
| 검사 | 위치 | 하는 일 | 막는 실수 |
|---|---|---|---|
| gate | 추출 직후 | 모델은 발언 **번호**만 고르고 인용문은 코드가 원문에서 복사. 확정·보류·진행·회상 표현 규칙, 원문에 없는 기한은 지움 | 인용 조작, 회상·제안을 결정으로 |
| 판정표 | 비교할 때 | 모델에게는 기준마다 같다·다르다만 묻고, 충돌 종류·승인 권한자는 코드 표가 결정 | 모델이 충돌을 지어내거나 빠뜨림 |
| 교차검증 | 위험한 판단 | 작은 모델 2개 × 질문 2가지(정방향·뒤집은 질문) = 4표. 이의 1표면 8b 재심, 2표 이상이면 확인 필요 | 같은 모델이 같은 쪽으로 틀림 |
| validate | 답 내기 직전 | 답의 결정 번호·숫자·날짜·인용이 근거에 글자 그대로 있는지 대조, LLM 심판 1~5점, 3회 실패면 원장 기록으로 답 | 근거에 없는 값, 상태 혼동 |

### 2.3 찾기 — 규정은 RAG로, 결정은 색인으로 좁혀서
사내 규정·아키텍처 가이드라인은 RAG에 넣고, 회의 결정이 이것과 부딪히면 '확인 필요'와 해결 방향으로 따로 알린다. 오탐을 줄여 온 과정은 세 단계였다.
1. **한곳에 섞기 → 4개로 분리.** 자료를 한 색인에 넣으니 이미 대체된 옛 결정이 새 결정과 같은 무게로 검색돼 오탐 2건. 규정·결정·기준 문서·원문으로 나누고 우선순위를 코드가 정하게 해 0건.
2. **점수 하한.** 비슷하기만 한 문장이 근거로 붙어서, 정답·함정 문장의 점수 분포로 하한을 정했다(주제 0.50, 원문 0.58). 못 넘으면 '찾지 못함'.
3. **결정은 별칭 색인.** 결정이 쌓이면 목록을 통째로 읽는 방식이 무너진다. 질문의 표현을 별칭 표로 주제에 잇고("Redis 캐시" → cache), 그 주제의 결정·미결 3~5건만 모델이 번호로 고른다. 어떤 별칭이 걸렸는지 남아 왜 그 후보인지 설명할 수 있다.

### 2.4 사람 승인과 운영
- **관리자 콘솔** — 승인함(근거 발언·근거 회의·대체될 결정·이전 논의), 열람 요청(범위·기간), 미결함(경과일·결정 없이 닫기), 회의 접근 권한, 처리 이력, 품질 감시
- **결정 수정 창** — 근거 발언 앞뒤 원문을 보며 고치고, 주제를 바꾸면 "승인하면 대체될 결정"을 바로 다시 보여 줌. 저장하면 원장·R3 색인·이력이 함께 갱신
- **새 주제는 사람이** — 목록 밖 사안이면 모델은 '새 주제'로만 표시하고, 팀장이 키·설명·별칭을 만든다(모델이 지은 주제 키는 버림)
- **열람 권한** — 회의는 기본적으로 참석자만. 권한 없는 결정은 내용 자체를 LLM에 넘기지 않음
- **파이프라인 감시** — 코드·프롬프트·임계값·어휘·모델의 지문으로 버전을 등록하고, 요청별 지표와 드리프트를 판정해 승격·롤백. 실제로 dev 셋 수정(689a7d3)이 할 일 기한 정정을 결정으로 뽑게 만든 회귀를 승격 게이트가 막았다(3.6)

### 2.5 파이프라인 감시 — 사람이 고친 흔적으로 놓친 것을 찾아 고친다
모델을 학습시키는 구조가 아니므로, 감시의 중심은 버전이 아니라 **사람이 고친 흔적**이다(`ledger/feedback.py`, 관리자 콘솔 '품질 감시' 맨 위 '사람이 고친 것에서 찾은 놓침').
1. **사람 신호** — 반려, 승인 전 수정, 주제 변경, 새 주제 만들기
2. **왜 놓쳤나 분류** — 이미 목록에 있던 주제로 고침 = 모델이 못 찾은 것 → 결정 문장에서 그 주제 별칭에 없는 낱말을 별칭 후보로 / 새 주제 = 목록 밖 사안 / 문장 수정 = 추출 품질 / 반려 = 사유와 함께
3. **팀장이 별칭 후보를 눌러 반영** — 색인을 바로 다시 만든다
4. **다음엔 찾음** — 반영된 놓침은 '반영됨'으로 표시해 고리가 닫혔는지 본다

**조용한 실패 막기** — 판정·기준 조회 실패, 추출 출력 잘림, 비교할 기준 없음을 '문제없음'·'결정 없음'으로 넘기지 않고 확인 필요·오류로 드러낸다. 시험 셋에서도 회의 처리 오류 1/20을 0건으로 숨기지 않고 오류로 셌다.

**전체 검증** — 처음 보는 회의 40개 dev·test, 오류 분석 원인 6개, 단위 테스트 198개. 운영 중에는 반려율·수정률·확인 필요율 등 14개 지표를 기준 30건과 최근 30건으로 비교해 10%p 이상 나빠지면 경보(같은 분포 200쌍에서 잘못 울린 경보 2.5%).

프롬프트·임계값·별칭을 바꿀 때마다 버전을 기록해, 무엇을 바꾼 뒤 나빠졌는지 거슬러 찾을 수 있게 했다(`scripts/promote.py`로 이전 상태 복원).

### 3.2 처음 보는 회의로 다시 잰 신뢰도 (회의 40 · 총 5만 1천 자 · 결정 200 · 질문 200)

47.5%가 말해 주는 것은 처음 보는 말은 모델이 틀릴 수밖에 없다는 점이다. 그래서 대응은 셋이다. ① 모르는 건 팀장에게 넘긴다(넘긴 것의 78.8%가 실제 애매·오류). ② 팀장이 고친 주제를 감시가 잡아 별칭·색인을 보강한다(2.5). ③ 규칙을 고칠 때는 평가와 승격 게이트로 확인한다.

## 4. 느낀 점 및 향후 개선 사항

### 4.1 진행하며 얻은 인사이트
1. **모델의 일을 줄일수록 결과를 믿을 수 있었다.** 충돌 목록을 모델에게 직접 쓰게 했더니 같은 정책을 열 번 반복하고 유효 결정을 빠뜨렸다. 모델에게는 "같다·다르다", "몇 번 발언"만 묻고 나머지를 코드로 옮기자 인용 조작과 충돌 누락이 구조적으로 사라졌다.
2. **작은 정답지의 100%는 과적합이었다.** 회의 3건에서 틀릴 때마다 규칙을 고쳤으니 100%가 나올 수밖에 없었다. 처음 보는 회의 40개로 재니 자동 처리 정확도는 절반이었고, dev에서 고친 규칙도 test에서는 남지 않았다. dev와 test를 나누고 test를 한 번만 돌리는 것이 숫자를 믿게 만드는 최소 조건이었다.
3. **'모른다'고 말하게 하는 것이 정확도만큼 중요했다.** 판정 실패가 '문제없음'으로, 출력 잘림이 '결정 없음'으로, 비슷하기만 한 문장이 '논의 있음'으로 조용히 바뀌는 경우를 하나씩 막았다. 그 결과 사람에게 넘긴 것의 79%가 실제로 애매하거나 틀린 건이었다. 자동 처리가 절반만 맞아도, 무엇을 넘길지를 잘 고르면 사람의 검토 시간을 줄일 수 있다.
4. **벡터 검색이 늘 답은 아니다.** 결정처럼 "같은 사안의 최신 상태"가 중요한 자료는 의미 유사도보다 주제 색인이 정확하고 설명 가능했다(400건에서 23% → 92%).
5. **보안 제약이 설계를 바꿨다.** 회의 원문은 이름을 가려도 '무엇을 정했는지'가 기밀이라 외부 LLM을 쓰지 않았다. 작은 로컬 모델의 판단력이 낮은 만큼 코드와 사람이 책임지는 범위를 넓혔고, 그게 '모든 결정은 사람 승인을 거치는 초안'이라는 구조로 이어졌다.
6. **감시는 사람이 고친 흔적에서 시작한다.** 모델을 학습시키지 않으니 버전 비교만으로는 무엇을 고칠지 알 수 없었다. 팀장이 이미 있던 주제로 고친 결정은 '모델이 못 찾은 것'이라는 가장 구체적인 신호여서, 거기서 별칭 후보를 뽑아 되먹이는 고리를 만들었다.
7. **측정 환경도 설계 대상이다.** 16GB 맥북에서 모델 호출이 겹치면 측정이 시간 초과로 멈췄고, 오래 켜 둔 Ollama가 굳어 평가가 계속 실패하기도 했다. 측정을 같은 기기·같은 조건에서 차례로 돌리도록 순서를 관리해야 시간 숫자를 비교할 수 있었다.

### 4.4 향후 개선
- **STT + 화자 분리 연동** — 지금은 화자가 적힌 전사문에서 시작한다. 녹음 → STT → 화자 분리 → 이 파이프라인으로 잇는다. 이 서비스는 'PM·PL이 확정했는가', '누가 처음 제안했는가'를 화자로 판단하므로 화자가 결정 판정의 열쇠다. 화자 확신이 낮은 발언은 '확인 필요'로 넘기고, 목소리도 생체 정보라 로컬에서 처리한다
- 첫 회의 온보딩 모드 — 새 프로젝트·새 영역이라고 밝히면 기존 주제에 억지로 맞추지 않고 용어를 모아 주제·별칭 후보로 올림
- 놓침 신호(색인 0건인데 전체 읽기로 찾음, 팀장의 주제 수정) → 별칭 후보함 → 팀장 승인으로 색인을 되먹임
- 결정 주제 정확도 개선 (처음 보는 회의에서 45%)
- 권한 판정에 금액·기간 기준값 비교 (지금은 역할만 봄)
- 결정 추출 안정화 (긴 회의의 출력 잘림)
- 실제 회의록으로 검증
- 사내 GPU 서버에 더 큰 오픈 모델
- 뜻이 같은 다른 문장의 답 재사용(의미 캐시)은 뜻이 반대인 질문에 잘못 답할 위험이 있어 보류
