## 1. 진행 사항 소개

### 1.1 선택한 과제
과제 2 신규 프로젝트. Base AI Agent(운영 인시던트 대응)의 노드 구조·의존성 주입·MCP·LangSmith 틀은 그대로 두고, 주제를 **회의에서 정한 것을 관리하는 에이전트**로 바꿨다. 강의 녹음을 Whisper로 전사해 정리하다가, 요약보다 "그래서 뭘 정했고 그게 예전 결정과 맞는지"를 찾는 데 시간이 더 든다는 것에서 출발했다.

### 1.2 해결하려는 문제 — 회의가 끝나면 사람이 하는 일

| 일 | 지금 하는 방식 | 이 에이전트 |
|---|---|---|
| 정리 | 회의록을 읽고 누가 뭘 정했는지, 할 일은 누구에게 갔는지 골라냄 | 결정·할 일·미결을 발언 번호와 함께 추출 |
| 비교 | 지난 결정·기준 문서·사내 규정을 뒤져 부딪히는 점을 정리 | 4종 기준과 자동 비교, 승인 권한자까지 해결 방향 |
| 근거 | "왜 그렇게 정했어?"가 오면 원문을 처음부터 다시 읽음 | 확정·승인 대기·미결·확인 필요·찾지 못함 라벨과 원문 인용 |
| 제안자 | 누가 처음 냈는지 찾아 다시 물어봄 | "누가 제안했어?" → 모델 없이 0.2초 |
| 보안 | 회의 내용이 기밀이라 외부 LLM에 맡기기 어려움 | 전부 로컬 모델(qwen3:8b) |

가상 프로젝트 회의 OPS-M04에서는 PM이 빠진 사이 이미 정한 SSE를 WebSocket으로 다시 결정하고, PL 혼자 운영 반영을 2주 미뤘다(2주 이상은 본부장 승인 사항). LLM에 회의록만 주면 사내 규정을 몰라 못 잡고, 흔한 RAG는 이미 대체된 옛 결정을 근거로 엉뚱한 충돌을 낸다.

### 1.3 주요 Task

## 2. 사용한 기술 요소

### 2.1 기술 요소별 적용

| 기술 요소 | 적용 내용 |

| RAG | Chroma 4종(R1 회의 원문 · R2 기준 문서 · R3 결정 · R4 사내 규정). 우선순위 R4 > 유효 결정 > R2 > R1을 코드가 해석. 결정 찾기는 벡터 대신 별칭 색인 |
| 의존성 주입 | `LedgerDeps`(모델·MCP·권한 판정)를 모든 노드에 `partial`로 주입. 테스트에서 가짜 LLM·MCP로 교체 |
| LangSmith | 노드·MCP 호출에 `@traceable`, 실행마다 파이프라인 버전을 메타데이터로 |
| 모듈화 | `agent/`(그래프·검색·보강·사실 질문) · `ledger/`(원장·RAG·색인·권한·감시·어휘) |
| 단위 테스트 | pytest 204개, Ollama 없이 수 초 |

### 2.2 파이프라인 — 모델은 고르기만, 판정은 코드, 확정은 사람

`분류 → 찾기 → 판정 → { 질문·의견은 바로 답 / 애매하면 '확인 필요' / 회의 결정은 팀장 승인 }`

- **분류** — 규칙이 먼저 가르고 애매할 때만 모델. 사실 질문은 모델 없이 0.2초
- **찾기** — 결정마다 MCP 도구로 규정·기준 문서·예외·권한표·원문을 모음
- **판정** — 충돌·권한 위반·승인된 변경을 가리고, 권한표 기준값·대체될 결정으로 해결 방향을 냄
- **보류** — 판정 실패, 비교할 기준 없음, 주제가 애매함 → 단정하지 않고 '확인 필요'

| 검사 | 하는 일 | 막는 실수 |
|---|---|---|
| gate (추출 직후) | 모델은 발언 **번호**만 고르고 인용문은 코드가 원문에서 복사. 확정·보류·회상 표현 규칙 | 인용 조작, 회상·제안을 결정으로 |
| 판정표 (비교할 때) | 모델에게는 같다·다르다만 묻고, 충돌 종류·승인 권한자는 코드 표가 결정 | 충돌을 지어내거나 빠뜨림 |
| validate (답 직전) | 결정 번호·숫자·날짜가 근거에 글자 그대로 있는지 대조, LLM 심판, 최대 3회 재작성 | 근거에 없는 값 |

### 2.3 찾기 — 규정은 RAG로, 결정은 색인으로

1. **한곳에 섞기 → 4개로 분리.** 한 색인에 넣으니 대체된 옛 결정이 새 결정과 같은 무게로 검색돼 오탐 2건 → 분리 후 0건
2. **점수 하한.** 정답·함정 문장의 점수 분포로 하한(주제 0.50)을 정하고, 못 넘으면 '찾지 못함'
3. **결정은 별칭 색인.** 질문 표현을 별칭 표로 주제에 잇고("Redis 캐시" → cache) 그 주제의 결정 3~5건만 모델이 번호로 고름. 왜 그 후보인지 설명할 수 있음

### 2.4 사람 승인과 파이프라인 감시

- **승인** — 승인함(근거 발언·대체될 결정), 근거 앞뒤 원문을 보며 고치는 수정 창, 새 주제·별칭은 사람이 만듦(모델이 지은 주제 키는 버림), 열람은 참석자만
- **사람이 고친 흔적으로 놓친 것 찾기** — 모델을 학습시키지 않으므로 감시의 중심은 사람의 수정이다. 팀장이 이미 있던 주제로 고친 결정 = 모델이 못 찾은 것 → 결정 문장에서 별칭 후보를 뽑고, 팀장이 누르면 색인을 다시 만든다(`ledger/feedback.py`)
- **조용한 실패 막기** — 조회 실패·출력 잘림·기준 없음을 '문제없음'·'결정 없음'으로 넘기지 않음. 탐지 정확도: 시험 셋에서 확인 필요로 넘긴 것 중 78.8%가 실제로 애매하거나 틀린 건
- **버전·승격** — 코드·프롬프트·임계값·별칭 지문으로 버전을 기록하고, 기준 평가에서 지표가 하나라도 떨어지면 승격 거부(3.5)

### 3.3 오류 분석 → 수정 → 원인 분류

| 원인 (dev 기준선) | 규모 | 수정 |
|---|---|---|
| '3번까지 재시도'의 '까지'를 할 일 기한으로 보고 결정에서 뺌 | 놓친 결정 22건 중 12 | 날짜·요일 앞의 '까지'만 기한 |
| 진행자(PM·PL) 발언을 무조건 결정으로 | 틀린 결정 72건 중 41 | 진행 발언·회상·질문·미루기 제외 |
| '~해도 될까요'가 잡담 경로로 → "결정되었습니다"라고 지어냄 | 질문·의견 25건 | 말투 규칙 추가 |
| 추출 출력이 잘려 결정 0건으로 조용히 넘어감 | 놓친 결정 5건 | 재시도, 두 번 실패면 오류로 드러냄 |

dev에서는 자동 처리 정확도가 48.8 → 53.8%로 올랐지만 test에서는 기준선 수준(구간 겹침)이었다. 비교 엔진은 동작한다 — 한 문장 의견이면 규정 충돌의 76.9%를 잡는다. 막히는 곳은 회의 대화에서 결정에 주제를 붙이는 단계(45%)다. 주제를 틀리면 비교할 기준을 못 찾는다.

| 분류 | 원인 | 대응 |
|---|---|---|
| 큰 모델이면 풀림 | 진행 발언을 결정으로 착각 · '~해도 될까요'를 잡담으로 · 출력 잘림 · 49개 중 주제 고르기 | 뉘앙스·긴 문맥 처리 → 사내 GPU에 더 큰 모델 |
| 모델과 무관 | '3번까지' 기한 오판 · 별칭에 없는 표현 · 권한 기준값 비교 · 첫 회의 기준 부족 | 코드 수정 · 팀장 보강 고리 · 코드 추가 · 첫 회의 온보딩 |

47.5%가 말해 주는 것은 처음 보는 말은 모델이 틀릴 수밖에 없다는 점이다. 그래서 ① 모르는 건 팀장에게 넘기고(넘긴 것의 78.8%가 실제 애매·오류) ② 팀장이 고친 주제로 별칭·색인을 보강하고 ③ 규칙 수정은 평가와 승격 게이트로 확인한다. 회의 원문은 외부로 보낼 수 없으므로, 가상 데이터셋으로 큰 모델의 상한부터 재고 사내 GPU 서버 도입을 판단한다.

## 4. 느낀 점 및 향후 개선 사항

### 4.1 진행하며 얻은 인사이트
1. **모델의 일을 줄일수록 결과를 믿을 수 있었다.** 충돌 목록을 모델에게 쓰게 하니 같은 정책을 열 번 반복하고 유효 결정을 빠뜨렸다. "같다·다르다", "몇 번 발언"만 묻고 나머지를 코드로 옮기자 인용 조작과 충돌 누락이 사라졌다.
2. **작은 정답지의 100%는 과적합이었다.** 처음 보는 회의 40개로 재니 절반이었고, dev에서 고친 규칙도 test에서는 남지 않았다. dev와 test를 나누고 test를 한 번만 돌리는 것이 숫자를 믿게 만드는 최소 조건이었다.
3. **'모른다'고 말하게 하는 것이 정확도만큼 중요했다.** 실패가 '문제없음'으로 조용히 바뀌는 경우를 하나씩 막자, 사람에게 넘긴 것의 79%가 실제로 애매하거나 틀린 건이 됐다. 자동 처리가 절반만 맞아도 무엇을 넘길지 잘 고르면 검토 시간을 줄일 수 있다.
4. **벡터 검색이 늘 답은 아니다.** "같은 사안의 최신 상태"가 중요한 결정은 의미 유사도보다 주제 색인이 정확하고 설명 가능했다(400건에서 23% → 92%).
5. **보안 제약이 설계를 바꿨다.** 회의 원문은 이름을 가려도 '무엇을 정했는지'가 기밀이라 외부 LLM을 쓰지 않았다. 로컬 모델의 판단력이 낮은 만큼 코드와 사람이 책임지는 범위를 넓혔고, 그게 '모든 결정은 사람 승인을 거치는 초안'이라는 구조로 이어졌다.

### 4.3 한계와 구현 난도

| 한계 | 왜 한계인가 | 구현 난도 |
|---|---|---|
| 화자 분리 | 확정 권한·제안자를 화자로 판단 → 화자를 틀리면 결정 판정이 틀림. 지금은 화자가 적힌 전사문을 가정 | 중간 — 겹쳐 말하기 오류, 목소리 등록, 생체 정보라 로컬 처리 |
| 정확도 (자동 47.5% · 주제 45%) | 규칙이 회의 말투마다 깨져 dev 개선이 test에서 안 남음 | 높음 — 근본은 더 큰 모델·실제 회의 데이터인데 외부 LLM 불가 → 사내 GPU |
| 교차검증 | 작은 모델 2개의 재검토를 옵션으로 넣었으나 dev에서 정확도 53.8 → 54.2%로 그대로, 넘기는 양만 44 → 70%. 약한 모델이 강한 모델을 검사하는 구조라 오류를 가려내지 못해 기본 끔 | 높음 — 검사 모델이 8b 이상이어야 의미 |
| 새 프로젝트 세팅 | 주제·별칭·권한표를 사람이 먼저 넣어야 하고, 첫 회의의 주제 실수가 다음 회의로 번짐 | 중간 — 첫 회의 온보딩(용어 후보 → 팀장 승인)으로 반자동 |

### 4.4 향후 개선
- **STT + 화자 분리 연동** — 녹음 → STT → 화자 분리 → 이 파이프라인. 화자 확신이 낮은 발언은 '확인 필요'로, 목소리도 로컬에서 처리
- 첫 회의 온보딩 모드 — 새 영역이면 기존 주제에 억지로 맞추지 않고 용어를 모아 주제·별칭 후보로
- 사람이 고친 사례를 평가 셋에 덧붙여 승격 게이트 기준을 키우기
- 권한 판정에 금액·기간 기준값 비교, 실제 회의록으로 검증, 사내 GPU 서버에 더 큰 오픈 모델
- 뜻이 같은 다른 문장의 답 재사용(의미 캐시)은 뜻이 반대인 질문에 잘못 답할 위험이 있어 보류
