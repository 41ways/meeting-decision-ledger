# 설계 결정 기록 (ADR)

대안이 있었던 선택만 적는다. 형식: 배경 → 고른 것 → 버린 대안 → 대가(트레이드오프).

## ADR-01 RAG를 4종으로 나눈다

- 배경: 회의록, 기준 문서, 결정, 정책은 같은 주제를 다른 시점·권위로 말한다. 한 저장소에 섞으면 옛 결정과 새 결정이 같은 무게로 검색된다.
- 고른 것: R1 원문(증거) · R2 기준 문서(현재 상태) · R3 결정 원장(변경 이력) · R4 정책·권한표(상위 규칙). 해석 순서는 R4 > R3 > R2 > R1.
- 버린 대안: 단일 컬렉션 + 메타데이터만 붙이기.
- 대가: 컬렉션 4개 관리, 검색 호출 수 증가. 실측에서 단순 RAG(Before-B)는 대체된 결정을 2번 근거로 들었고 After는 0번.

## ADR-02 "지금 유효한 기준"은 코드가 정한다

- 배경: LLM에게 여러 버전을 주고 고르게 하면 구버전(정책 v2의 MySQL 표준, 요구사항 v1.0의 5초)을 집어 든다.
- 고른 것: `resolve_current`(MCP Tool)가 SQLite 원장 상태로 유효 결정·현행 버전만 골라 준다. 대체된 결정, 구 정책은 판정 단계에 아예 들어가지 않는다.
- 대가: 주제 키(topic)가 틀리면 엉뚱한 기준을 가져온다. 주제 선택은 LLM이 목록에서 고르는 방식이라 오분류 가능성이 남는다.

## ADR-03 인용문은 코드가 원문에서 채운다

- 배경: LLM에게 인용을 쓰게 하면 말을 다듬거나 여러 발언을 이어 붙인다. 근거가 근거 역할을 못 한다.
- 고른 것: LLM은 발언 번호(seq)만 고르고 인용은 코드가 원문에서 복사한다. validate가 글자 단위로 다시 대조한다.
- 대가: 번호를 잘못 고르면 엉뚱한 발언이 인용된다. 그래서 gate가 "확정 발언 + 3발언 이내 제안"으로 범위를 좁힌다.

## ADR-04 결정 후보는 규칙, 요약은 LLM

- 배경: qwen3:8b에게 회의록 전체에서 결정을 뽑게 하니 "그렇게 진행하죠"처럼 짧은 승인 발언을 놓치고, 할 일 배정을 결정으로 섞었다.
- 고른 것: 확정 표현(걸로/겠습니다/하죠…)과 진행자(PM·PL)의 단정 발언을 코드가 후보로 표시하고, LLM은 후보를 분류·요약한다. 보류 표현("아직 확정은 아닙니다")은 코드가 뺀다.
- 버린 대안: LLM 단독 추출 (실측 결정 정밀도 77%).
- 대가: 한국어 표현 규칙이 데이터에 맞춰져 있다. 다른 말투의 회의에서는 규칙 보강이 필요하다. 진행자 단정 발언 규칙은 회상 발언을 진행자가 하면 오탐할 수 있다.

## ADR-05 충돌 판정: LLM은 관계만, 분류는 판정표

- 배경: 처음엔 LLM이 충돌 목록을 직접 쓰게 했다. 같은 정책(ARC-02)을 10번 반복하고 유효 결정 OPS-0007은 빠뜨렸다.
- 고른 것: LLM은 기준마다 same / different / unrelated만 답한다. 충돌 종류(정책·과거 결정·기준 문서·다른 프로젝트 참고·기준 변경)는 코드 판정표 `decide()`가 정한다. 권한 위반은 LLM과 무관하게 권한표로 코드가 붙인다.
- 대가: 판정표가 단순해서 "같은 방향이지만 범위가 다른" 미묘한 경우를 표현하지 못한다. 예외(waiver) 범위 판단은 여전히 LLM에 의존한다.

## ADR-06 로컬 모델 (qwen3:8b, think off)

- 배경: 회의록·면접 기록은 사내 기밀이고 지원자 개인정보다. 외부 API로 보내면 이 프로젝트가 잡아내는 정책(SEC-01)을 스스로 어긴다.
- 고른 것: Ollama 로컬 모델. 분류·추출은 thinking을 끈다(출력 1,000토큰 → 수십 토큰).
- 대가: 처리 시간이 의견·질의 포함 평균 25~28초, 회의 1건 60~80초이고 큰 모델보다 판단 품질이 낮다. 그래서 ADR-03~05처럼 코드가 책임지는 범위를 넓혔다. 출력 반복을 막으려고 출력 길이 상한(num_predict)과 컨텍스트(num_ctx 16k)를 명시했다.

## ADR-07 승인은 사람만, API 버튼으로

- 배경: 결정이 원장에 들어가면 이후 판단의 기준이 된다. 잘못 들어가면 오류가 전파된다.
- 고른 것: 그래프는 문제없는 결정을 "승인 대기"로 올리기까지만 한다. 승인은 화면 버튼(`POST /decisions/{id}/approve`)으로 사람이 한다. 승인되면 같은 주제의 기존 결정은 삭제하지 않고 대체(superseded) 표시만 한다.
- 버린 대안: LangGraph `interrupt`로 그래프를 멈추고 기다리기. 체크포인터와 재개 흐름이 필요해 설명·구현 부담이 커서 뺐다.
- 대가: 승인 대기가 쌓이면 병목이 된다. 승인 전까지 그 결정은 권위가 없다.

## ADR-08 예외(waiver)는 정책을 바꾸지 않는다

- 배경: 사람이 정책 예외를 승인해야 할 때가 있다(백도어). 하지만 일시적 승인으로 정책 문서가 바뀌면 안 된다.
- 고른 것: 예외는 별도 표(waivers)에 대상 규칙·프로젝트·범위·만료일과 함께 둔다. 판정 때 범위와 만료를 확인해 "예외 범위 안에서 가능"으로만 표시한다. 정책 개정은 새 버전(v4)을 만드는 경로뿐이다.
- 대가: 범위 문구 해석("마스킹 샘플")은 LLM이 한다.

## ADR-09 면접 전사문은 판정하지 않는다

- 배경: 같은 구조로 면접 요약에 쓸 수 있지만 채용 판단을 AI가 하면 공정성 문제가 생긴다.
- 고른 것: 루브릭 역량별 요약 + 지원자 발언 인용 + 공정성 점검(직무 무관 개인정보 질문, 면접 중 합격 확정)까지만. 점수·합격 여부는 내지 않는다.
- 대가: 요약 문장 자체의 편향(말투에 따른 인상)은 막지 못한다. 근거 인용으로 사람이 대조할 수 있게만 했다.

## ADR-10 일정 추가는 코드가 해석하고 사람이 저장, 저장소는 인터페이스 뒤에

- 배경: "다음 주 화요일 오후 3시 회의 잡아줘"를 LLM에 맡기면 날짜 계산(다음 주의 기준, 오전·오후)이 흔들리고, 빠진 시간을 그럴듯하게 채운다. 구글 팀 달력 연동도 요구되지만 계정·인증 없이 개발해야 한다.
- 고른 것: 날짜·시간은 규칙(`ledger/schedule_parse.py`, 상대 주는 일정 조회 `_range`와 같은 규칙)으로, LLM은 제목·참석자·프로젝트만 뽑고 코드가 원문·users.json·projects.json과 대조한다. 모르는 값은 빈칸으로 두고 되묻는다. 그래프는 초안만 만들고, 저장은 화면에서 '추가'를 누른 뒤 `POST /events`에서만 한다. 저장소는 `CalendarProvider` 인터페이스로 감싸 로컬 SQLite가 기본이고, 구글은 필드 매핑·호출 지점만 둔 스텁이다.
- 버린 대안: LLM이 날짜·시간까지 JSON으로 내기 / 그래프가 바로 저장 / 처음부터 구글 달력을 원본으로 쓰기.
- 대가: 규칙에 없는 표현("담주 화욜", "점심 먹고")은 빈칸이 되어 사람이 채워야 한다. 오전·오후 없는 1~7시는 오후로 보고 그 사실을 카드에 적는다. 구글 연결 전에는 팀 달력과 겹침 검사를 하지 못한다.
