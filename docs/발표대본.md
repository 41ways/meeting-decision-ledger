# 발표 대본 (5분: 발표 3분 + 시연 2분)

장표: https://claude.ai/artifact/QRWEgspT5Meao14ndZDdTM (7장). 괄호 안은 누적 시간.

시연 전: 서버 켜기(`bash sh/run.sh`) → 정한결(팀장)로 로그인. 리허설 때는 승인 버튼을 누르지 않는다(누르면 `bash scripts/reset_demo.sh`로 되돌림).

---

## 1. 표지 (0:00–0:05)

회의 요약 · 결정 정리 비서를 만든 정한결입니다. 회의록을 요약하는 데서 멈추지 않고, 회의에서 정한 것을 관리하는 에이전트입니다.

## 2. 문제 — 회의가 끝나면 사람이 하는 일 5가지

(0:05–0:35) 강의 녹음을 Whisper로 정리하다가 시작한 주제입니다. 회의가 끝나면 사람이 하는 일이 다섯 가지 있습니다.
누가 뭘 정했는지 정리하고, 지난 결정이나 사내 규정과 뭐가 달라졌는지 비교하고, 몇 주 뒤 질문이 오면 왜 그렇게 정했는지 원문을 다시 찾고, 이 아이디어를 누가 냈는지 찾아 다시 물어봅니다. 그런데 회의 내용 자체가 기밀이라 외부 LLM에 맡기기도 어렵습니다.
실제로 가상 프로젝트 회의에서, PM이 빠진 사이 이미 정한 SSE를 WebSocket으로 바꾸고, PL 혼자 운영 반영을 2주 미뤘는데 아무도 몰랐습니다.
LLM에 회의록만 주면 사내 규정을 몰라 못 잡고, 흔한 RAG는 이미 바뀐 옛 결정을 근거로 들어 엉뚱한 충돌을 냅니다.

## 3. 파이프라인

(0:35–1:25) 질문이나 회의록이 들어오면 먼저 무슨 종류인지 가릅니다. 규칙이 먼저 가르고 애매할 때만 모델이 고릅니다. 그래서 '누가 승인했어?' 같은 사실 질문은 모델을 안 거치고 0.2초에 답합니다.
그다음 비교할 기준을 찾고 판정합니다. 애매하면 단정하지 않고 '확인 필요'로 사람에게 넘기고, 원장에는 팀장이 승인한 것만 들어갑니다.
신뢰도를 올리는 검사가 네 곳 있습니다. gate: 모델은 발언 번호만 고르고 인용문은 코드가 원문에서 복사합니다. 판정표: 모델에게는 같다·다르다만 묻고 충돌 종류와 승인 권한자는 코드 표가 정합니다. 교차검증: 위험한 판단만 계열이 다른 작은 모델 둘에게 질문을 두 방향으로 물어 4표를 받고, 이의가 나오면 사람에게 넘깁니다. validate: 답을 내기 직전에 결정 번호·숫자·인용이 근거에 글자 그대로 있는지 대조합니다.
역할 분리형 멀티 에이전트입니다. 8b가 추출·판정, 작은 모델 둘이 검토, 확정은 사람. 원장 승인은 MCP 서버의 사람 전용 도구로만 됩니다.

## 4. 찾기 — 규정은 RAG, 결정은 색인

(1:25–2:00) 찾는 대상에 따라 방법을 나눴습니다. 사내 규정과 아키텍처 가이드라인은 RAG에 넣고, 회의 결정이 이것과 부딪히면 '확인 필요'와 해결 방향으로 따로 알려 줍니다.
오탐을 줄여 온 과정은 세 단계입니다. 처음엔 자료를 한곳에 섞었더니 옛 결정을 근거로 오탐이 나서, 규정·결정·기준 문서·원문 넷으로 나누고 무엇이 우선인지는 코드가 정하게 했습니다. 다음은 비슷하기만 한 문장이 근거로 붙는 문제라, 정답과 함정 문장의 점수 분포로 하한을 정해 못 넘으면 '찾지 못함'이라고 답합니다. 마지막으로 결정은 벡터 검색 대신 별칭 색인으로 좁혀 모델이 번호만 고르게 했습니다.
오른쪽이 그 효과입니다. 결정이 400건 쌓이면 통째로 읽기는 23%로 무너지지만, 좁힌 뒤 읽기는 92%, 1초 남짓입니다.

## 5. Before / After · 신뢰도

(2:00–2:45) 같은 입력으로 세 방식을 비교하면, LLM 단독은 사내 규정을 몰라 충돌을 하나도 못 잡고, 단순 RAG는 88%를 잡지만 이미 바뀐 옛 결정을 근거로 들어 오탐이 납니다. 이 에이전트는 100%였습니다.
그런데 이 100%는 규칙을 그 3건에 맞춘 결과였습니다. 그래서 처음 보는 회의 40개로 셋을 만들어 dev에서 틀린 원인 여섯 가지를 찾아 고쳤고(dev 48.8%에서 53.8%), test는 마지막에 한 번만 돌렸습니다.
test에서 자동으로 처리한 것의 정확도는 47.5%, 절반 수준입니다. 그래서 원장에 자동으로 쓰지 않고 모든 결정이 팀장 승인을 거치는 초안으로 둔 설계가 맞다고 봅니다. 대신 사람에게 넘긴 것의 78.8%는 실제로 애매하거나 틀린 건이라, 무엇을 넘길지는 쓸 만하게 고릅니다.

## 6. 한계 · 다음 단계 (STT + 화자 분리)

(2:45–3:00) 한계입니다. 외부 LLM을 쓰지 않아 회의 정리가 3분 가까이 걸리고, 처음 보는 회의에서는 결정의 주제를 맞히는 정확도가 45%입니다. dev에서 고친 효과가 test에서는 남지 않았습니다.
다음 단계로 가장 하고 싶은 것은 STT와 화자 분리 연동입니다. 이 주제가 강의 녹음을 Whisper로 정리하다가 시작됐습니다. 지금은 화자가 적힌 전사문에서 시작하지만, 녹음을 넣으면 화자 분리를 거쳐 결정 원장까지 이어지게 하려고 합니다. 이 서비스에서는 화자가 특히 중요합니다. PM·PL이 확정했는지, 누가 처음 제안했는지를 화자로 판단하기 때문입니다. 그래서 화자 확신이 낮은 발언은 '확인 필요'로 넘기고, 목소리도 생체 정보라 로컬에서 처리합니다. 이제 화면으로 보겠습니다.

## 7. 시연 (3:00–5:00)

(3:00–5:00) 정한결(팀장)로 로그인한 상태에서 시작. 로컬 모델로 회의 정리를 돌리면 3분 가까이 걸려서, 대화방에는 미리 실제로 돌린 결과를 넣어 두었습니다.
1. 왼쪽 대화 목록 'OPS-M04 회의 정리해줘' → 스크롤: 결정 4건 중 확인 필요 3건, 2주 연기는 권한표 기준과 숫자로 비교해 본부장 승인 필요(2주 미만이면 PM), 맨 아래 눈여겨볼 점.
2. 위 '관리자 콘솔' → 왼쪽 '결정·의견 승인' → OPS-0011 줄 클릭(근거 발언·대체될 결정 펼침) → '문장·주제 수정' → 왼쪽 근거 발언 노란 강조, '앞 3발언 더 보기' 한 번 → 주제를 realtime.transport로 바꾸면 '승인하면 대체될 결정: OPS-0007'이 바로 뜸 → '취소' → '승인'.
3. 위 '대화' → 왼쪽 'Redis 캐시 쓰기로 했어?' → Redis 캐시는 기각한 대안, 세션 저장소 결정과 엮여 확인 필요로 넘긴 이유 → 입력창에 '이거 누가 승인했어?' → 방금 승인한 정한결 → '누가 제안했어?' → 장상민 (둘 다 모델 없이 표 조회).
4. 왼쪽 '세션 저장소를 Redis로 바꾸면 어때?' → 기존 결정 OPS-0008과 충돌, 해결 방향.
5. '관리자 콘솔' → 왼쪽 맨 아래 '품질 감시' → 파이프라인 버전과 드리프트 판정. 감사합니다.

## 예상 질문

- **Multi-Agent가 맞나?** → 감독자가 하위 에이전트를 부르는 구조는 아닙니다. 역할을 나눈 구조입니다: 8b가 추출·판정, 계열이 다른 작은 모델 둘이 위험한 판단만 검토, 확정은 사람. 그래프 안에서는 계획·조사·분석·검증을 노드로 나눴습니다.
- **교차검증이 의미가 있나? 온도 0인데?** → 온도 0이면 같은 모델에 다시 물어도 같은 답이라 의미가 없습니다. 그래서 다른 계열 모델 두 개에, 질문을 정방향과 뒤집은 방향으로 물어 4표를 받습니다. 작은 모델의 무조건 yes 버릇은 뒤집은 질문이 걸러 줍니다. 이의가 결과를 자동으로 뒤집지는 않고 사람에게 넘깁니다. 다만 켜서 쓰는 옵션이고(CROSSCHECK=1), 이번 신뢰도 측정은 끈 상태로 해서 효과는 아직 재지 못했습니다.
- **왜 외부 API를 안 썼나?** → 회의 원문은 이름을 가려도 무엇을 정했는지(기술·예산·일정·고객사)가 기밀입니다. 마스킹으로 안전해지지 않습니다. 대신 로컬 8b의 한계를 좁힌 뒤 읽기로 넘었고, 외부 API는 실제 데이터가 없는 평가 도구에만 쓸 수 있습니다.
- **100%가 너무 높은데?** → 작은 정답지(회의 3)의 100%는 규칙을 그 3건에 맞춘 결과였습니다. 처음 보는 시험 셋(회의 20·질문 100, 1회)에서는 자동 처리 정확도 47.5%(95% 구간 39.4–55.7), 결정 재현율 77%, 정밀도 54.6%입니다. 그래서 원장에는 사람 승인만 기록합니다.
- **절반이면 쓸 수 있나?** → 자동으로 확정하는 도구가 아니라 초안 작성기입니다. 사람에게 넘긴 48.7% 중 78.8%가 실제로 애매하거나 틀린 건이라, 팀장이 볼 곳을 좁혀 주는 데 쓸 만합니다. 회의 처리 오류 1건도 조용히 0건으로 내지 않고 오류로 드러냈습니다.
- **고쳤는데 왜 안 올랐나?** → dev 오류를 분석해 결정·기한 규칙을 고쳤고 dev에서는 정확도 48.8→53.8%, 재현율 78→85%였지만 시험 셋은 기준선 수준입니다. 구간이 겹쳐 일반화됐다고 말할 수 없습니다. 시험 셋을 보고 다시 고치지는 않았습니다.
- **결정을 왜 RAG로 안 찾나?** → 의미가 비슷하다는 이유로 엉뚱한 결정이 붙습니다. 예: "Redis 캐시 쓰기로 했어?"가 Redis를 기각한 세션 저장소 결정에 붙습니다. 별칭 색인은 어떤 표현이 걸렸는지 남아서 설명할 수 있고, 목록이 커져도 정답률이 유지됩니다.
- **새 주제가 나오면?** → 모델은 '새 주제'라고만 표시하고 이름은 팀장이 승인 화면에서 정합니다. 모델이 이름을 지으면 같은 사안이 매번 다른 이름으로 갈라져 '같은 주제의 새 결정이 옛 결정을 대체한다'는 규칙이 깨집니다. 주제 없는 결정은 승인 버튼이 막힙니다.
- **같은 뜻의 다른 질문은?** → 찾기는 별칭으로 같은 주제에 닿아 답은 대개 같고, 저장된 답 재사용만 글자가 같을 때로 한정했습니다. 뜻이 반대인 질문에 잘못된 답을 줄 위험이 시간 절약보다 커서입니다.
- **승인을 LangGraph interrupt로 안 한 이유?** → 승인은 몇 시간에서 며칠 뒤에 일어납니다. 그래프를 멈춰 두면 대기 상태가 체크포인터에 묶이고, 서버를 다시 켜면 사라집니다. 승인 대기를 원장 상태로 두면 재시작해도 남습니다 (ADR-07).
- **LLM이 지어내면?** → 인용은 코드가 원문에서 복사하고, 원문에 없는 담당자·기한·숫자는 지우거나 다시 쓰게 하고, 세 번 실패하면 원장 기록으로 답합니다. 원장에는 사람이 승인한 것만 들어갑니다.
