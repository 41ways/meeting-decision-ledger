# 발표 대본 (5분, 장표 10장)

장표: https://claude.ai/artifact/QRWEgspT5Meao14ndZDdTM (버전 31). 괄호 안은 누적 시간. 시연은 5번 기능 장에서 화면으로 넘어가 진행한다.

시연 전: 서버 켜기(`bash sh/run.sh`) → 정한결(팀장)로 로그인. 리허설 때는 승인 버튼을 누르지 않는다(누르면 `bash scripts/reset_demo.sh`로 되돌림).

---

## 1. 표지 (0:00–0:05)
AI 회의록 정리 비서를 만든 정한결입니다.

## 2. 문제 · 페인포인트 (0:05–0:30)
회의가 끝나면 사람이 하는 일이 다섯 가지 있습니다. 누가 뭘 정했는지 정리하고, 지난 결정이나 규정과 뭐가 달라졌는지 비교하고, 왜 그렇게 정했는지 근거를 찾고, 이 아이디어를 누가 냈는지 찾아 다시 물어봅니다. 그런데 회의 내용은 기밀이라 외부 LLM에 맡기기도 어렵습니다. 실제로 PM이 빠진 회의에서 이미 정한 방식을 뒤집고 일정을 2주 미뤘는데 아무도 몰랐습니다.

## 3. 해결 방법 (0:30–0:50)
이 다섯 가지를 이렇게 줄입니다. 결정과 할 일을 자동으로 뽑되 인용은 원문에서 그대로 복사하고, 규정·결정·기준 문서와 자동으로 비교해 누가 승인해야 하는지까지 냅니다. 근거는 라벨과 원문으로 답하고, 제안자는 모델 없이 바로 찾습니다. 전부 로컬 모델로 돌리고, 원장에는 팀장이 승인한 것만 들어갑니다.

## 4. 파이프라인 (0:50–1:40)
들어온 말은 규칙으로 먼저 분류하고 애매할 때만 모델이 고릅니다. 그래서 사실 질문은 0.2초입니다. RAG는 넷으로 나눴습니다. 한곳에 섞으니 이미 바뀐 옛 결정이 새 결정과 같은 무게로 검색돼 오탐이 났기 때문입니다. 결정은 색인으로 좁혀서 400건에서도 23%가 92%가 됩니다. 위험한 판단은 계열이 다른 작은 모델 두 개가 질문 두 방향으로 다시 봐서 4표를 받고, 이의가 둘 이상이면 보류합니다. 재 보니 결정·질문에 대한 이의는 절반이 실제 오류였고, 기준과의 관계는 헛경보라 기본값은 꺼 뒀습니다. 보류는 기준과 부딪힐 때, 주제가 애매할 때, 검증 이의가 날 때, 처리가 실패할 때입니다.

## 5. 기능 + 시연 (1:40–3:10)
화면으로 보겠습니다.
- 회의 정리 방: "결정 4건 중 3건이 확인 필요입니다. 2주 연기는 권한표와 숫자로 비교해 본부장 승인이 필요하다고 알려 줍니다."
- 관리자 콘솔 → 결정·의견 승인 → OPS-0011 → 문장·주제 수정: "근거 발언 앞뒤를 보며 고치고, 주제를 바꾸면 대체될 결정이 바로 보입니다." → 취소 → 승인
- 'Redis 캐시 쓰기로 했어?' 방: "Redis는 기각한 대안으로 나오고, 비슷한 결정이 있어 확인 필요로 넘겼습니다." → "이거 누가 승인했어?" → 방금 승인한 정한결 → "누가 제안했어?" → 장상민 (둘 다 모델 없이)
- '세션 저장소를 Redis로 바꾸면 어때?' 방: "기존 결정과 충돌하고 해결 방향까지 냅니다."

## 6. 정확도 · 신뢰도 (3:10–3:40)
같은 입력으로 비교하면 LLM 단독은 충돌을 못 잡고, 단순 RAG는 옛 결정으로 오탐을 내고, 이 에이전트는 100%였습니다. 그런데 처음 보는 회의로 test를 한 번 돌리니 자동 처리 정확도는 47.5%, 절반입니다. 그래서 원장에 자동으로 쓰지 않고 모두 팀장 승인을 거칩니다. 대신 사람에게 넘긴 것의 78.8%는 실제로 애매하거나 틀린 건이었습니다. 교차검증을 켜도 넘기는 양만 늘고 정확도는 그대로였습니다.

## 7. 왜 떨어지나 · 해결 과정 (3:40–4:10)
찾고 비교하는 부분은 동작합니다. 한 문장 의견은 규정 충돌의 77%를 잡습니다. 그런데 회의 대화에서는 12.5%입니다. 결정을 뽑고 주제를 맞히는 단계가 병목이고, 주제 정확도가 45%입니다. dev에서 원인 여섯 가지를 찾아 고쳐 48.8%가 53.8%가 됐지만, test에서는 47.5%로 일반화되지 않았습니다.

## 8. 한계 (4:10–4:40)
첫째, 화자 분리입니다. 이 서비스는 누가 확정했고 누가 제안했는지를 화자로 판단해서, 녹음에서 바로 쓰려면 화자 분리가 열쇠입니다. 겹쳐 말하기와 생체 정보 문제로 난도는 중간입니다. 둘째, 정확도는 규칙을 늘리면 과적합이라 더 큰 모델과 실제 데이터가 필요해 가장 어렵습니다. 셋째, 새 프로젝트는 주제와 별칭을 사람이 먼저 넣어야 해서, 첫 회의를 용어를 모으는 회의로 다루는 반자동을 생각하고 있습니다.

## 9. 파이프라인 감시 (4:40–4:55)
고칠 때마다 정확도가 떨어지지 않았는지 지킵니다. 모델·프롬프트·임계값·주제 중 하나라도 바뀌면 새 버전으로 등록하고, 지표 14개를 기준과 비교해 나빠지면 경보를 내고, 지표가 하나도 안 떨어져야 승격합니다. 나빠지면 이전 버전으로 되돌립니다.

## 10. 감사합니다 (4:55–5:00)
모델은 고르기만, 판정은 코드, 확정은 사람. 감사합니다.

## 예상 질문

- **Multi-Agent가 맞나?** → 감독자가 하위 에이전트를 부르는 구조는 아닙니다. 역할을 나눈 구조입니다: 8b가 추출·판정, 계열이 다른 작은 모델 둘이 위험한 판단만 검토, 확정은 사람. 그래프 안에서는 계획·조사·분석·검증을 노드로 나눴습니다.
- **교차검증이 의미가 있나? 온도 0인데?** → 온도 0이면 같은 모델에 다시 물어도 같은 답이라 의미가 없습니다. 그래서 다른 계열 모델 두 개에, 질문을 정방향과 뒤집은 방향으로 물어 4표를 받습니다. 작은 모델의 무조건 yes 버릇은 뒤집은 질문이 걸러 줍니다. 이의가 결과를 자동으로 뒤집지는 않고 사람에게 넘깁니다. 다만 켜서 쓰는 옵션이고(CROSSCHECK=1), 이번 신뢰도 측정은 끈 상태로 해서 효과는 아직 재지 못했습니다.
- **왜 외부 API를 안 썼나?** → 회의 원문은 이름을 가려도 무엇을 정했는지(기술·예산·일정·고객사)가 기밀입니다. 마스킹으로 안전해지지 않습니다. 대신 로컬 8b의 한계를 좁힌 뒤 읽기로 넘었고, 외부 API는 실제 데이터가 없는 평가 도구에만 쓸 수 있습니다.
- **100%가 너무 높은데?** → 작은 정답지(회의 3)의 100%는 규칙을 그 3건에 맞춘 결과였습니다. 처음 보는 시험 셋(회의 20·질문 100, 1회)에서는 자동 처리 정확도 47.5%(95% 구간 39.4–55.7), 결정 재현율 77%, 정밀도 54.6%입니다. 그래서 원장에는 사람 승인만 기록합니다.
- **절반이면 쓸 수 있나?** → 자동으로 확정하는 도구가 아니라 초안 작성기입니다. 사람에게 넘긴 48.7% 중 78.8%가 실제로 애매하거나 틀린 건이라, 팀장이 볼 곳을 좁혀 주는 데 쓸 만합니다. 회의 처리 오류 1건도 조용히 0건으로 내지 않고 오류로 드러냈습니다.
- **고쳤는데 왜 안 올랐나?** → dev 오류를 분석해 결정·기한 규칙을 고쳤고 dev에서는 정확도 48.8→53.8%, 재현율 78→85%였지만 시험 셋은 기준선 수준입니다. 구간이 겹쳐 일반화됐다고 말할 수 없습니다. 시험 셋을 보고 다시 고치지는 않았습니다.
- **결정을 왜 RAG로 안 찾나?** → 의미가 비슷하다는 이유로 엉뚱한 결정이 붙습니다. 예: "Redis 캐시 쓰기로 했어?"가 Redis를 기각한 세션 저장소 결정에 붙습니다. 별칭 색인은 어떤 표현이 걸렸는지 남아서 설명할 수 있고, 목록이 커져도 정답률이 유지됩니다.
- **새 주제가 나오면?** → 모델은 '새 주제'라고만 표시하고 이름은 팀장이 승인 화면에서 정합니다. 모델이 이름을 지으면 같은 사안이 매번 다른 이름으로 갈라져 '같은 주제의 새 결정이 옛 결정을 대체한다'는 규칙이 깨집니다. 주제 없는 결정은 승인 버튼이 막힙니다.
- **같은 뜻의 다른 질문은?** → 찾기는 별칭으로 같은 주제에 닿아 답은 대개 같고, 저장된 답 재사용만 글자가 같을 때로 한정했습니다. 뜻이 반대인 질문에 잘못된 답을 줄 위험이 시간 절약보다 커서입니다.
- **승인을 LangGraph interrupt로 안 한 이유?** → 승인은 몇 시간에서 며칠 뒤에 일어납니다. 그래프를 멈춰 두면 대기 상태가 체크포인터에 묶이고, 서버를 다시 켜면 사라집니다. 승인 대기를 원장 상태로 두면 재시작해도 남습니다 (ADR-07).
- **LLM이 지어내면?** → 인용은 코드가 원문에서 복사하고, 원문에 없는 담당자·기한·숫자는 지우거나 다시 쓰게 하고, 세 번 실패하면 원장 기록으로 답합니다. 원장에는 사람이 승인한 것만 들어갑니다.
