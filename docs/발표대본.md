# 발표 대본 (5분, 장표 15장)

장표: https://claude.ai/artifact/QRWEgspT5Meao14ndZDdTM. 괄호 안은 누적 시간. 시연은 5–8번 기능 장(한 장에 화면 하나)에서 화면으로 넘어가 진행한다.

시연 전: 서버 켜기(`bash sh/run.sh`) → 정한결(팀장)로 로그인. 리허설 때는 승인 버튼을 누르지 않는다(누르면 `bash scripts/reset_demo.sh`로 되돌림).

---

## 1. 표지 (0:00–0:05)
AI 회의록 정리 비서를 만든 정한결입니다.

## 2. 문제 (0:05–0:25)
회의가 끝나면 사람이 하는 일이 다섯 가지 있습니다. 누가 뭘 정했는지 정리하고, 지난 결정·규정과 뭐가 달라졌는지 비교하고, 왜 그렇게 정했는지 근거를 찾고, 그 아이디어를 누가 냈는지 찾습니다. 그런데 회의 내용은 기밀이라 외부 LLM에 맡길 수 없습니다. 실제로 PM이 빠진 회의에서 이미 정한 방식이 바뀌고, PL 혼자 일정을 2주 미뤘는데 아무도 몰랐습니다.

## 3. 해결 방법 (0:25–0:45)
그래서 회의록을 넣으면 언제 누가 무엇을 정했는지 원문 인용과 함께 뽑고, 예전 결정·회사 규정과 다르면 누구 승인이 필요한지까지 알려 줍니다. '왜 그렇게 정했어?', '누가 제안했어?'에도 원문으로 답합니다. 데이터는 회사 밖으로 나가지 않고, 최종 기록은 팀장이 승인한 것만 남습니다. 회의 내용을 사람마다 따로 전달하지 않아도, 비서 한 창구에서 모두가 같은 근거로 답을 얻습니다.

## 4. 파이프라인 (0:45–1:20)
들어온 말은 규칙으로 먼저 분류하고 애매할 때만 모델이 고릅니다. 그래서 사실 질문은 모델 없이 0.2초입니다. 찾기는 RAG를 규정·결정·문서·원문 넷으로 나눴습니다. 한곳에 섞으니 이미 바뀐 옛 결정이 새 결정과 같은 무게로 검색됐기 때문이고, 결정은 색인으로 좁혀 400건에서도 23%가 92%가 됐습니다. 판정 뒤에는 세 갈래입니다. 질문·의견은 근거와 함께 바로 답하고, 부딪히거나 확신이 없으면 '확인 필요'로 표시하고, 회의 결정은 팀장이 승인하기 전엔 원장에 들어가지 않습니다.
(질문 대비: 인용은 코드가 원문에서 그대로 복사, 답을 내기 직전 번호·숫자를 근거와 한 번 더 맞춤, 그래도 애매하면 팀장에게)

## 5–8. 기능 + 시연 (1:20–2:50)
화면으로 보겠습니다.
- (5) 회의 정리: "OPS-M04를 정리하면 결정 4건 중 3건이 확인 필요입니다. 2주 연기는 규정과 부딪히고, 권한표상 본부장 승인이 필요하다고 알려 줍니다. 2주 미만으로 줄이면 PM 승인으로 된다는 해결 방향도 같이 줍니다."
- (6) 관리자 콘솔 → 승인함 → OPS-0011: "근거 발언 앞뒤 원문을 보며 고치고, 주제를 바꾸면 무엇이 대체되는지 저장 전에 보입니다." → 취소 → 승인
- (7) 'Redis 캐시 쓰기로 했어?': "Redis는 기각한 대안이고, 지금 결정은 아직 승인 대기라고 구분해 답합니다." → "이거 누가 승인했어?" → "누가 제안했어?" (둘 다 모델 없이)
- (8) '세션 저장소를 Redis로 바꾸면 어때?': "기존 결정 OPS-0008과 충돌한다고 알려 주고, 팀장이 승인하면 대체된다는 해결 방향까지 냅니다."

## 9. 정확도 · 신뢰도 (2:50–3:15)
같은 입력으로 비교하면 LLM 단독은 사내 규정을 몰라 0%, 단순 RAG는 옛 결정으로 오탐을 내 88%, 이 비서는 100%였습니다. 그런데 이건 회의 3건에 맞춘 결과라, 처음 보는 회의 40개, 총 5만 1천 자로 셋을 만들어 test를 한 번만 돌렸습니다. 자동 처리 정확도는 47.5%, 절반입니다. 그래서 원장에 자동으로 쓰지 않고 모두 팀장 승인을 거칩니다. 대신 사람에게 넘긴 것의 78.8%는 실제로 애매하거나 틀린 건이었습니다.
(질문 대비: 회의당 약 1,300자, 말 사이 공백을 감안하면 10분 안팎 회의 분량 · 교차검증을 켜도 넘기는 양만 44→70%로 늘고 정확도는 그대로)

## 10. 틀린 이유와 고친 것 (3:15–3:35)
처음 보는 회의에서 틀린 것을 열어 보니 원인이 이렇습니다. '3번까지'의 '까지'를 기한으로 봐서 날짜 앞 '까지'만 기한으로 고쳤고, 진행 발언을 결정으로 본 것은 진행·회상·질문을 뺐고, '~해도 될까요'를 잡담으로 보낸 것은 말투 규칙을 넣었고, 출력이 잘려 '결정 0건'이 되던 것은 다시 시도하고 실패는 오류로 드러냅니다. 주제를 잘못 고르는 것은 팀장이 고친 주제로 별칭을 보강하고, 첫 회의의 기준 부족은 첫 회의 온보딩으로 풉니다.
(질문 대비: 놓친 결정 12, 틀린 결정 41, 말투 25건, 잘림 5건 · dev 48.8 → 53.8%, test 47.5%)

## 11. 로컬 모델 성능이 오르면 풀리는 부분 (3:35–3:45)
이 중 주황색 네 가지는 지금 작은 로컬 모델이라 규칙으로 막은 것들입니다. 로컬 모델의 성능이 올라가면 충분히 해결되는 부분이고, 아래 두 가지는 팀장 보강과 온보딩으로 풉니다.

## 12. 모델을 키우면 풀리는 것, 아닌 것 (3:45–4:05)
정리하면, 뉘앙스·말투·긴 문맥, 49개 주제 중 고르기는 큰 모델이면 풀리고, 별칭에 없는 표현·권한 기준값 비교·첫 회의 기준 부족은 모델과 무관하게 코드와 팀장 보강으로 풉니다. 회의 원문은 외부로 못 보내니, 가상 데이터셋으로 큰 모델의 상한부터 재고 사내 GPU 서버 도입을 판단하려 합니다. 47.5%가 말해 주는 건 처음 보는 말은 모델이 틀릴 수밖에 없다는 것이고, 그래서 모르는 건 팀장에게 넘기고, 고친 흔적으로 보강하고, 규칙은 게이트로 확인합니다.

## 13. 한계 (4:05–4:30)
남은 한계는 셋입니다. 첫째, 화자 분리입니다. 누가 확정했고 누가 제안했는지를 화자로 판단해서, 녹음에서 바로 쓰려면 화자 분리가 열쇠입니다. 겹쳐 말하기와 생체 정보 문제로 난도는 중간입니다. 둘째, 정확도는 규칙을 늘리면 과적합이라 더 큰 모델과 실제 데이터가 필요해 가장 어렵습니다. 셋째, 새 프로젝트는 주제·별칭·권한표를 사람이 먼저 넣어야 해서 첫 회의 온보딩으로 반자동화하려 합니다.

## 14. 파이프라인 감시 (4:30–4:55)
모델을 학습시키는 게 아니라서 감시는 사람이 고친 흔적에서 시작합니다. 팀장이 이미 있던 주제로 고쳤다면 모델이 못 찾은 것이라 별칭 후보를 올리고, 팀장이 누르면 다음엔 찾습니다. 실패나 출력 잘림은 '문제없음'으로 넘기지 않고 확인 필요로 드러냅니다. 실제로 막은 사례도 있습니다. dev를 보고 고친 규칙이 '10월 13일 회의 전까지로 할게요'라는 기한 정정을 결정으로 뽑게 만들었는데, 사람은 몰랐지만 결정 정밀도가 100에서 92로 떨어져 승격 게이트가 거부했습니다. 원인을 고치고 다시 재 100으로 통과했습니다.

## 15. 감사합니다 (4:55–5:00)
모델은 고르기만, 판정은 코드, 확정은 사람. 감사합니다.

## 예상 질문

- **Multi-Agent가 맞나?** → 감독자가 하위 에이전트를 부르는 구조는 아닙니다. 역할을 나눈 구조입니다: 8b가 추출·판정, 계열이 다른 작은 모델 둘이 위험한 판단만 검토, 확정은 사람. 그래프 안에서는 계획·조사·분석·검증을 노드로 나눴습니다.
- **교차검증이 의미가 있나? 온도 0인데?** → 온도 0이면 같은 모델에 다시 물어도 같은 답이라 의미가 없습니다. 그래서 다른 계열 모델 두 개에, 질문을 정방향과 뒤집은 방향으로 물어 4표를 받습니다. 작은 모델의 무조건 yes 버릇은 뒤집은 질문이 걸러 줍니다. 이의가 결과를 자동으로 뒤집지는 않고 사람에게 넘깁니다. 다만 dev에서 켜 보니 정확도는 53.8→54.2%로 그대로이고 넘긴 비율만 44→70%로 늘어 의미가 없었습니다. 검사 모델이 8b보다 약해서 오류를 가려내지 못합니다. 그래서 기본값은 껐고 발표에서는 뺐습니다.
- **왜 외부 API를 안 썼나?** → 회의 원문은 이름을 가려도 무엇을 정했는지(기술·예산·일정·고객사)가 기밀입니다. 마스킹으로 안전해지지 않습니다. 대신 로컬 8b의 한계를 좁힌 뒤 읽기로 넘었고, 외부 API는 실제 데이터가 없는 평가 도구에만 쓸 수 있습니다.
- **100%가 너무 높은데?** → 작은 정답지(회의 3)의 100%는 규칙을 그 3건에 맞춘 결과였습니다. 처음 보는 시험 셋(회의 20·질문 100, 1회. 셋 전체는 회의 40개 · 총 5만 1천 자, 회의당 약 1,300자 — 말 사이 공백을 감안하면 10분 안팎 회의 분량)에서는 자동 처리 정확도 47.5%(95% 구간 39.4–55.7), 결정 재현율 77%, 정밀도 54.6%입니다. 그래서 원장에는 사람 승인만 기록합니다.
- **절반이면 쓸 수 있나?** → 자동으로 확정하는 도구가 아니라 초안 작성기입니다. 사람에게 넘긴 48.7% 중 78.8%가 실제로 애매하거나 틀린 건이라, 팀장이 볼 곳을 좁혀 주는 데 쓸 만합니다. 회의 처리 오류 1건도 조용히 0건으로 내지 않고 오류로 드러냈습니다.
- **고쳤는데 왜 안 올랐나?** → dev 오류를 분석해 결정·기한 규칙을 고쳤고 dev에서는 정확도 48.8→53.8%, 재현율 78→85%였지만 시험 셋은 기준선 수준입니다. 구간이 겹쳐 일반화됐다고 말할 수 없습니다. 시험 셋을 보고 다시 고치지는 않았습니다.
- **결정을 왜 RAG로 안 찾나?** → 의미가 비슷하다는 이유로 엉뚱한 결정이 붙습니다. 예: "Redis 캐시 쓰기로 했어?"가 Redis를 기각한 세션 저장소 결정에 붙습니다. 별칭 색인은 어떤 표현이 걸렸는지 남아서 설명할 수 있고, 목록이 커져도 정답률이 유지됩니다.
- **새 주제가 나오면?** → 모델은 '새 주제'라고만 표시하고 이름은 팀장이 승인 화면에서 정합니다. 모델이 이름을 지으면 같은 사안이 매번 다른 이름으로 갈라져 '같은 주제의 새 결정이 옛 결정을 대체한다'는 규칙이 깨집니다. 주제 없는 결정은 승인 버튼이 막힙니다.
- **같은 뜻의 다른 질문은?** → 찾기는 별칭으로 같은 주제에 닿아 답은 대개 같고, 저장된 답 재사용만 글자가 같을 때로 한정했습니다. 뜻이 반대인 질문에 잘못된 답을 줄 위험이 시간 절약보다 커서입니다.
- **승인을 LangGraph interrupt로 안 한 이유?** → 승인은 몇 시간에서 며칠 뒤에 일어납니다. 그래프를 멈춰 두면 대기 상태가 체크포인터에 묶이고, 서버를 다시 켜면 사라집니다. 승인 대기를 원장 상태로 두면 재시작해도 남습니다 (ADR-07).
- **LLM이 지어내면?** → 인용은 코드가 원문에서 복사하고, 원문에 없는 담당자·기한·숫자는 지우거나 다시 쓰게 하고, 세 번 실패하면 원장 기록으로 답합니다. 원장에는 사람이 승인한 것만 들어갑니다.
