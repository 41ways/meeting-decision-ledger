# 발표 대본 (5분)

장표: https://claude.ai/artifact/QRWEgspT5Meao14ndZDdTM (9장)
말하는 속도 기준 분당 약 280자. 괄호 안은 누적 시간.

시연 전: 서버를 끄고 `bash scripts/reset_demo.sh` → 서버 다시 켜기 → 정한결로 로그인해 둔다.

---

## 1. 표지 (0:00–0:15)

회의 요약 · 결정 정리 비서를 만든 정한결입니다.
회의록을 요약하는 데서 멈추지 않고, 회의에서 **정한 것**을 관리하는 에이전트입니다.

## 2. 문제 (0:15–0:50)

회의에서 정한 게 제대로 남지 않고, 뒤집혀도 아무도 모르는 문제가 있습니다.
가상 프로젝트에 자주 생기는 세 상황을 넣었습니다.
PM이 빠진 회의에서 이미 정한 SSE를 WebSocket으로 바꿉니다. PL이 혼자 운영 반영을 2주 미루는데, 원래 본부장 승인 사항입니다. 옛 정책 문서를 근거로 MySQL을 고릅니다.
LLM에 회의록만 주면 사내 규칙을 몰라 못 잡고, 흔한 RAG는 이미 바뀐 옛 결정을 근거로 들어 엉뚱한 충돌을 냅니다.

## 3. 해법 (0:50–1:20)

기능은 셋입니다. 결정과 할 일을 근거 발언과 함께 뽑고, 과거 결정·기준 문서·사내 정책·결정 권한과 부딪히는지 본 뒤 **해결 방향**까지 냅니다. 예를 들어 "2주 연기"는 권한표 기준값과 숫자로 비교해 "본부장 승인이 필요하고, 2주 미만으로 줄이면 PM 승인으로 된다"고 알려 줍니다. 나중에 물으면 확정인지, 승인 대기인지, 미결인지 라벨을 붙여 원문까지 찾아 답합니다.
오른쪽이 OPS-M04 결과입니다. 결정 4건 중 3건이 확인 필요이고, 문제없는 1건만 승인 대기로 올라갑니다. 회의 기록이 남아서, 지난 회의에서 미결이던 캐시가 이 회의 결정으로 이어진 것도 보여 줍니다.
결정 원장에 실제로 들어가는 건 **팀장이 승인한 것뿐**입니다.

## 4. RAG 4종 (1:20–1:50)

같은 주제를 회의록, 기준 문서, 결정, 정책이 서로 다른 시점과 권위로 말합니다. 한곳에 섞으면 옛 결정과 새 결정이 같은 무게로 검색됩니다.
그래서 넷으로 나누고 우선순위를 정했습니다. 정책이 가장 위, 그다음 승인된 결정, 기준 문서, 회의 원문은 인용 근거로만 씁니다.
지금 유효한 기준은 LLM이 아니라 코드가 고릅니다. 그래서 대체된 결정 인용이 2건에서 0건이 됐습니다.

## 5. 그래프 (1:50–2:30)

강사님 베이스의 노드 이름과 순서, 의존성 주입은 그대로 두고 노드 안만 바꿨습니다. 여러 에이전트가 대화하는 구조가 아니라, 역할을 노드로 나눈 역할 노드형입니다.
원칙은 하나입니다. **LLM은 읽고 분류만 하고, 판정과 기록은 코드와 사람이 합니다.**
LLM은 기준마다 "같은가 다른가"만 답하고, 충돌 종류는 코드 판정표가 정합니다. 인용문도 LLM은 발언 번호만 고르고 문장은 코드가 원문에서 복사합니다.
validate에서는 인용 글자를 대조하고, 질의 답변은 LLM 심판이 1~5점을 매겨 3점 미만이면 다시 씁니다.
검색 결과도 그대로 믿지 않습니다. 정답과 함정 문장의 점수 분포를 재서 하한을 정했고, LLM이 고른 주제와 문장 검색 결과가 어긋나면 단정하지 않고 '확인 필요'로 넘깁니다.
MCP 서버로 도구 18개를 분리했고, LangSmith로 노드별 실행을 추적했습니다.

## 6. 화면과 권한 (2:30–2:55)

베이스 채팅 화면을 사내 포털처럼 바꿨습니다. 역할은 팀장, 담당자, 팀원, 인턴 넷이고, 회의는 기본적으로 참석자만 봅니다.
못 보는 회의는 열람 요청을 하고, 팀장이 범위와 기간을 정해 승인합니다. 권한 없는 결정은 LLM에도 넘기지 않습니다.

## 7. Before / After (2:55–3:40)

같은 입력을 세 방식으로 돌렸습니다.
단순 RAG도 충돌은 88% 잡지만, 대체된 결정을 근거로 들어 오탐이 2건 나옵니다. 우리 방식은 0건입니다.
LLM 단독은 할 일 기한 연도를 2023년으로 지어냈습니다. 원문에 없는 담당자나 날짜는 코드가 지워서 100%가 됐습니다.
대가도 있습니다. 처리 시간은 LLM 단독의 2.8배, 호출은 4.5배입니다. 해결 방향과 회의 기록을 만드는 호출이 늘어서인데, gpt-4o-mini 단가로 환산하면 전체가 1.2센트 정도입니다.
그리고 **100%는 제가 만든 작은 정답지 기준**입니다. 일반화된 성능이라고 말씀드리기는 어렵습니다.

## 8. 문제와 한계 (3:40–4:15)

개발 중 문제는 대부분 LLM에게 맡긴 일을 코드로 옮겨서 풀었습니다.
LLM에게 충돌 목록을 직접 쓰게 했더니 같은 정책을 열 번 반복해서 판정표로 바꿨고, 짧은 단정 발언을 놓쳐서 누락 재확인을 넣었습니다.
이 교육에서 가장 경계한 조용한 폴백도 막았습니다. 논의한 적 없는 주제에 아무 발언이나 붙여 "미결정"이라 답하던 것, 주제를 못 정하면 가장 가까운 주제를 억지로 붙이던 것, 판정이 실패했는데 "문제없음"이 나오던 것을 모두 '찾지 못함'이나 '확인 필요'로 바꿨습니다.
한계는 작은 정답지(검색 하한도 같은 셋으로 정했습니다), LLM과 검색이 같은 쪽으로 틀리면 못 잡는다는 점, 그리고 운영 감시가 아직 없다는 점입니다.

## 9. 시연 (4:15–5:00)

(미리 만든 대화방을 보여 주며)
서지후가 OPS-M04를 정리하면 확인 필요 3건과 해결 방향, 승인 요청이 나옵니다. 정한결로 바꾸면 승인함에서 원문 인용과 '승인하면 대체될 결정'을 보고 OPS-0011을 승인합니다. 미결함에는 아직 결론 안 난 논의가 경과일과 함께 있습니다.
"캐시는 어떻게 하기로 했어?"라고 물으면 [승인 대기] 라벨과 지난 회의의 미결이 함께 나오고, "이거 누가 승인했어?"라고 이어 물으면 LLM 없이 표에서 바로 답합니다.
대화방의 기존 대화는 실제 결과를 옮긴 목업이고, 회의 정리는 한 건에 1분 남짓 걸립니다. 감사합니다.

## 예상 질문

- **Multi-Agent가 맞나?** → 하나의 StateGraph에서 계획·조사·분석·검증을 역할 노드로 나눈 형태입니다. 서브그래프 Supervisor 구조는 아닙니다.
- **100%가 너무 높은데?** → 제가 만든 결정 11·의견 5·질의 6건 기준이고, 틀린 걸 고친 뒤 같은 데이터로 다시 쟀습니다. 실제 회의록 검증이 다음 단계입니다.
- **왜 로컬 8B?** → 회의록이 사내 기밀이라 외부 API로 보내지 않는 쪽을 골랐습니다. 대신 판단 품질이 낮아서 코드가 책임지는 범위를 넓혔습니다.
- **승인을 LangGraph interrupt로 안 한 이유?** → 승인은 몇 시간 뒤에 일어나서, 그래프를 멈춰 두기보다 원장 상태(승인 대기)와 API 버튼으로 처리했습니다 (ADR-07).
- **검색이 엉뚱한 걸 가져오면?** → 점수 하한을 정답·함정 분포로 정했고(주제 0.50, 원문 0.58), 하한 미만이면 "찾지 못함"으로 답합니다. LLM이 고른 주제와 문장 검색 결과가 어긋나면 "확인 필요"로 사람에게 넘깁니다.
- **에이전트라면서 판단만 하나?** → 충돌마다 해결 방향을 냅니다. 승인 권한자와 기준값 비교, 적용 가능한 예외와 범위, 승인하면 대체되는 결정은 코드가 표에서 꺼내고, 대안 문장은 'AI 제안'으로 표시해 사람이 검토합니다.
- **지난 회의와 어떻게 이어지나?** → 회의 기록에 미결·할 일·요약을 남기고, 같은 주제의 앞선 미결을 다음 결정에 잇습니다. 말이 없다고 결정된 것으로 보지 않고, 기한이 지난 미결은 미결함에서 팀장에게 묻습니다.
- **LLM이 지어내면?** → 인용은 코드가 원문에서 복사하고, 원문에 없는 담당자·기한은 지우고, 원장에는 사람이 승인한 것만 들어갑니다.
