## 4. 우리가 앞선 점 — 발표에서 강조

1. **사람 승인과 역할 권한이 끝단까지** — 팀장 승인, 역할 4종, 열람 요청(범위·기간), 승인 대기가 DB 상태라 재시작에도 남음. 승인 흐름이 있는 다른 곳은 한 곳(interrupt + 메모리 체크포인터, 역할 권한 없음)
2. **"지금 유효한 기준"을 코드가 해석** — 정책 > 유효 결정 > 현행 문서 > 원문, 대체·구버전은 판정에서 제외. 실측으로 대체된 결정 인용 2건 → 0건. 다른 곳은 시행일 정렬까지
3. **3방식 Before/After와 비용 환산** — LLM 단독·단순 RAG·After를 같은 입력으로. 대가(시간 2.8배·호출 4.5배·1.2센트)까지 공개
4. **검색 하한을 정답·함정 점수 분포로 정함** — `eval/retrieval_eval.py`. 동기 저장소에 검색 하한을 잰 곳이 없음
5. **충돌 다음 단계(해결 방향)** — 권한표 기준값을 숫자로 비교해 승인자 안내, 예외 범위, 대체될 결정. 판정 뒤 해결 방향까지 내는 곳은 없음

①~④가 끝나면 추가 후보: 회의 단위 신뢰구간이 붙은 자동 처리율(동기 중 자동 처리율 개념을 가진 곳 없음), 목록 크기별 후보 곡선(후보 좁히기를 한 곳도 29건·상위 8 고정 규모).

## 5. 결정 추출(④)·신뢰도 지표(①) 설계 참고

### 5.1 결정 추출 — "지어냄 구조적 0, 누락은 표시, 진행자 확인"

- **상태는 코드가 정한다**: 자동 / 보류(사유 코드) / 근거 없음 / 미처리. 모델이 낸 처분을 코드가 다시 판정하고, 근거 검증 실패는 삭제가 아니라 보류로 낮춘다 (tashkeel `check_items`)
- **근거 검증 순서**: 발언 ID 존재 → 인용이 그 발언의 부분 문자열(공백·NFKC 정규화 후) → 결정의 핵심 값(대상·숫자·기한)이 인용 안에 있음. 사유 코드 예: `utterance_not_found`, `quote_not_in_utterance`, `value_not_in_quote`, `ambiguous_source` (tashkeel 5종, Repro 출처 보정)
- **출처 보정은 한 방향만**: 인용이 다른 발언 한 곳에서만 나오면 발언 ID만 고치고 기록. 여러 곳이면 거부. 문장 자체는 코드가 고치지 않음 (Repro `_resolve_evidence`)
- **누락 탐지는 독립 신호로**: 확정 표현이 있는데 어떤 결정의 근거로도 쓰이지 않은 발언 → 누락 의심. 작은 모델은 그다음 (tashkeel `suspected_missed`, req-trace `guard_route` 선례)
- **상태별 필드 상호배타**: 진행자 확인 필요 → 질문 필수·결정 내용 비움 (Repro `VerificationPlan`)
- **불확실하면 넘기는 쪽**: 놓치는 쪽이 더 위험한 판정은 보수적으로 둔다는 방향을 문서에 명시 (disaster `mcp_server/alert_state.py`)
- **근거 강제의 대가를 재라**: 근거를 강제하자 인용 정확도 0.2→0.8, 완전성 0.4→0.2로 떨어진 실측이 있다 (policy README). 누락 탐지기·진행자 확인이 필요한 이유로 인용 가능
- **작은 모델 이의 단계의 중단 기준을 미리**: "8b 단독이 합격선을 넘으면 이의 단계를 넣지 않는다"를 실행 전에 고정 (tashkeel `judge`의 stop 분기)
