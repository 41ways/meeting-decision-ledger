# 처음부터 다시 짠다면 — 서비스 설계안

지금 구현(meeting-decision-ledger)을 바탕으로, 처음부터 설계한다고 가정한 안. 코드는 바꾸지 않았다.
요구사항: 전사문 → 회의 요약·기록, 나중에 질문만으로 근거 있는 답, 확정인지 확인 필요인지 구분, 직급·사람별 접근과 승인·일정 관리, 사내 규정 대조.

---

## 1. 원칙

1. **원본 · 기록 · 색인 · 요약을 분리한다.** 원문은 고치지 않고 기한이 되면 지운다. 기록(DB)이 진실이다. 색인은 기록에서 언제든 다시 만들 수 있다. 요약은 사람이 읽는 용도다.
2. **LLM은 읽고 분류만 한다.** 사실(날짜·사람·숫자), 상태, 권한, 규정 판정은 코드와 사람이 정한다.
3. **상태는 사건으로만 바뀐다.** 제안 → 승인 → 대체, 미결 → 결정/종료. 침묵은 사건이 아니다.
4. **권한은 검색 전에 거른다.** 볼 수 없는 내용은 LLM 입력에도 들어가지 않는다.
5. **모르면 모른다.** 검색 하한 미달, 주제 불일치, 판정 실패는 '찾지 못함' 또는 '확인 필요'.
6. **모든 처리는 다시 돌릴 수 있고, 다시 돌려도 같은 것을 두 번 만들지 않는다.** 파이프라인 버전·모델·프롬프트를 기록하고, 재처리 결과는 이전과의 차이로 보여 준다.

## 2. 데이터

### 2.1 진실 = 관계형 DB

| 표 | 내용 | 보존 |
|---|---|---|
| `meetings` | 회의 ID, 프로젝트, 날짜, 제목, 참석자·역할, 열람 범위 | 영구 |
| `utterances` | 발언 (번호, 화자, 역할, 내용) | 90일 뒤 파기 |
| `topics` | 주제 키, 설명, 예시 문장, 상위 주제 | 관리자가 관리 |
| `threads` | **사안**: 같은 주제의 제안·논의·결정·대체를 회의를 가로질러 묶은 단위 | 영구 |
| `items` | 회의에서 나온 것: 종류(결정 후보/미결/할 일/논의), 문장, 주제, 사안, 근거 발언 번호·인용, 상태, 연결된 결정 | 결정 관련은 영구, 미결은 최소 정보만 |
| `decisions` (원장) | 승인된 결정, 이유, 기각 대안, 결정자, 승인자, 시행일, 대체 관계, 근거 인용 | 영구, 추가만 |
| `action_items` | 담당, 기한, 상태, 나온 항목 | 영구 |
| `policies` · `authority` · `waivers` | 정책 조항 버전, 결정 권한표(임계값 포함), 예외(범위·기한) | 버전 관리 |
| `documents` | 기준 문서 버전·조항 | 버전 관리 |
| `users` · `access_rules` · `grants` · `requests` | 역할, 회의별 열람 규칙, 열람 승인(범위·기간), 요청 | 영구 |
| `calendar_events` | 일정 (회의와 연결 가능), 공개 범위 | 영구 |
| `events` | 모든 상태 변화 이력: 누가, 언제, 무엇을, 왜 | 영구 |

`events`가 있으면 "이 결정은 언제 누가 승인했고, 그 전엔 어떤 상태였나"를 언제든 되돌려 볼 수 있다. 색인 갱신도 이 사건을 받아서 한다(4.6).

### 2.2 상태 라벨 (사용자에게 보이는 다섯 가지)

| 라벨 | 뜻 | 근거 |
|---|---|---|
| **확정** | 원장 승인, 지금 유효 | `decisions.status=approved`, 대체 안 됨 |
| **승인 대기** | 회의에서 확정 표현, 팀장 승인 전 | `items` 결정 후보 + 승인 요청 |
| **확인 필요** | 나왔지만 단정할 수 없음: 확정 표현이 애매함, 권한 위반, 규정 충돌, 주제 불확실, 판정 실패 | 판정표·가드 결과 |
| **미결** | 보류 명시 또는 논의만. 마지막 논의일·후속 담당 표시 | `items` 미결 |
| **찾지 못함** | 관련 기록 없음 | 검색 하한 미달 |

### 2.3 사안(thread) — "캐시 어떻게 하기로 했어?"에 흐름으로 답하기

한 사안 = 같은 주제의 시간순 기록. 예:

```
사안: 캐시 적용 범위 (cache)
  OPS-M03 10/06  제안   "자주 묻는 질문은 레디스 캐시에"      장상민
  OPS-M03 10/06  미결   "대상부터 정하자, 다음에"            서지후   → 할 일: 후보 정리(장상민, 10/13)
  OPS-M04 10/13  결정   "런북 문서에만 캐시"                 서지후   → OPS-0011 승인 대기
```

질문에는 사안의 **지금 상태**(승인 대기)를 먼저 답하고, 흐름은 접어서 보여 준다. 미결이 결정에 연결되는 것도 사안 안에서 일어난다.

## 3. 파이프라인

### 3.1 수집
1. 입력 어댑터: 클로바노트·팀즈·Whisper 출력 → 공통 형식
2. 화자 → 사람 목록 매칭 (못 맞추면 사람에게 확인 화면), 역할 부여
3. 용어집으로 STT 오인식 교정 (원문은 그대로 두고 교정본을 따로)
4. `meetings`·`utterances` 저장, 기본 열람 범위 = 참석자

### 3.2 회의 정리 (일괄 처리, 느려도 정확하게)

| 단계 | 누가 | 하는 일 | 실패하면 |
|---|---|---|---|
| 1 후보 표시 | 규칙 | 확정 표현 → 결정 후보, 보류 → 미결, 기한·부탁 → 할 일 | — |
| 2 분류 | LLM | 후보를 결정/미결/할 일/논의로, 근거 발언 번호 | 파싱 실패 → 회의 전체 '추출 실패', 원장 제안 안 함 |
| 3 게이트 | 코드 | 인용 원문 복사, 원문에 없는 담당·기한 삭제, 회상·보류 제거 | — |
| 4 누락 감사 | 코드+LLM | 모든 발언에 처리 결과 기록, 확정 표현인데 분류 안 된 발언 재확인 → 남으면 '누락 의심' | 보고서에 표시 |
| 5 주제·사안 | LLM+코드 | 주제 배정 → 두 경로 대조(주제 자료와의 유사도, 다른 주제 유사 결정) → 기존 사안에 연결 또는 새 사안 | 어긋나면 확인 필요 |
| 6 규정 대조 | LLM+판정표 | 정책 > 유효 결정 > 기준 문서. LLM은 같다/다르다만, 충돌 종류는 판정표. 권한표 임계값(기간·금액)은 코드가 숫자로 비교 | 판정 실패 → 확인 필요 |
| 7 미결 연결 | 코드+LLM | 같은 사안의 열린 미결이 있으면 이번 결정에 연결 | 애매하면 확인 필요 |
| 8 해결 제안 | 코드+LLM | 충돌마다 (1) 승인 권한자 (2) 적용 가능한 예외와 범위 차이 (3) 대안: 기각된 대안·이전 결정 (4) 요청 문안 초안 | — |
| 9 요약 | LLM | 주제·논의·미결·방향, 항목마다 근거 번호. 근거 번호가 원문에 없으면 그 줄 삭제 | — |
| 10 산출 | 코드 | 회의록 보고서, `items` 저장, 찾기 열쇠 생성, 승인함에 올림, 처리 버전 기록 | — |

### 3.3 질문 (온라인)

먼저 질문 종류를 가른다 (규칙 우선, 애매하면 LLM).

| 종류 | 예 | 처리 | LLM |
|---|---|---|---|
| 사실 조회 | 언제 회의? 참석자? 누가 결정? 지난주 몇 건? | SQL | 없음 |
| 근거 질문 | 캐시 어떻게 하기로 했어? SSE 왜 골랐어? | RAG(4장) → 원장·원문에서 코드가 근거 블록 → LLM 한두 문장 + 값 대조 | 문장만 |
| 의견 검토 | Redis로 바꾸면? | 규정 대조 판정표 → 해결 제안 | 같다/다르다, 문장 |
| 일정 | 다음 주 화요일 3시 회의 잡아줘 | 날짜는 코드가 해석 → 확인 카드 → 저장 | 제목·참석자 추출만 |
| 잡담 | 고마워 | 작은 모델, 사실 진술 금지 | 작은 모델 |

모든 답에 2.2의 라벨과 근거(회의·발언·결정 ID)를 붙인다. 숫자·날짜·ID는 근거와 글자 대조하고, 세 번 실패하면 원장 기록으로 만든 답으로 바꾼다.

### 3.4 승인과 상태 관리
- **승인함**: 결정 문장과 원문 인용 나란히, 승인하면 대체될 결정 미리보기, 주제 확인 경고, 해결 제안. 승인·반려 사유는 고정 분류(주제 틀림 / 요약 틀림 / 권한 / 규정 / 기타)로 받는다 — 반려 사유가 곧 품질 데이터다(6.3).
- **미결함**: 열린 미결 목록. 후속 할 일 기한이 지났거나 N주 언급이 없으면 팀장에게 "결정됐나요 / 계속 보류 / 종료"를 묻는다. 회의 밖에서 정해진 것은 사람이 여기서 닫는다.
- **열람 요청함**: 범위(이 사람/같은 역할/전체)·기간(1회/프로젝트 기간/무기한/날짜) 승인.

### 3.5 보존
매일 실행: 기한이 지난 회의의 `utterances`와 미결 상세 삭제, 발언 색인에서도 삭제. 남는 것: `meetings`, 원장(인용 포함), 결정 찾기 열쇠, 미결 최소 항목(주제·마지막 회의·담당자). 삭제도 `events`에 기록.

## 4. RAG — 무엇을 어떻게 찾나

### 4.1 무엇을 색인하고 무엇은 안 하나

| 색인 | 넣는 것 | 쓰는 곳 | 보존 |
|---|---|---|---|
| **K 찾기 열쇠** (핵심) | 결정·미결 항목마다: 대표 문장 1 + 예상 질문 2~4 + 주제 이름. 한 항목에 여러 벡터, 모두 같은 항목 ID | 근거 질문 | 결정은 영구, 미결은 원문과 함께 |
| **P 정책** | 현행 정책 조항, 권한표 설명 | 의견·결정의 규정 대조 | 버전별 (현행만 검색) |
| **B 기준 문서** | 현행 기준 문서 조항 | 규정 대조, 결정 없는 주제의 기준 | 버전별 |
| **U 발언** (선택) | 발언 + 앞뒤 1발언 묶음 | "어디서 얘기했지?", 누락 감사 | 90일 |

**색인하지 않는 것**: 회의 날짜·참석자·결정자·상태 같은 사실(SQL로 조회), 요약(사람용), 결정 본문(원장에서 읽음). 벡터 검색은 "뜻이 비슷한 것"을 찾는 도구라 정확한 사실을 꺼내는 데 쓰지 않는다.

색인마다 점수 분포가 달라서 **하한도 색인마다 따로** 정한다(4.5).

### 4.2 메타데이터 (모든 벡터에)

`item_id`, `kind`(decision/open/action/policy/doc/utterance), `status`, `project`, `topic`, `thread`, `meeting_id`, `date`, `acl`(볼 수 있는 역할·사람), `superseded`, `embed_model`(임베딩 모델 버전), `source_hash`(원본이 바뀌었는지 확인용)

### 4.3 예상 질문 만들기 (K)

- 결정이 **승인될 때**, 미결이 **만들어질 때** 생성한다.
- LLM에게 "이 결정을 찾을 사람이 물을 법한 질문 3개"를 받되, 코드가 검사한다:
  - 질문에 결정 문장이나 근거 발언의 핵심어가 하나 이상 있어야 한다
  - 근거에 없는 숫자·날짜·이름이 있으면 버린다
  - 다른 항목의 질문과 너무 비슷하면(같은 질문이 두 결정을 가리키면) 버린다
- 답 문장은 저장하지 않는다. 질문 → 항목 ID → 원장·원문에서 답.

### 4.4 근거 질문의 검색 순서

> 2026-10-21 구현은 이 순서의 2~4단계(벡터·재순위·하한)를 **별칭·ID 낱말 색인 → 50건 이내 LLM 선택**으로 바꿨다. 벡터는 기준 문서·정책에만 쓴다. 근거와 측정은 §8과 `eval/list_scaling.md`.

```
질문
 │ 1 정규화   용어집 동의어 확장(웹소켓=WebSocket), 결정 ID는 바로 SQL 조회
 │ 2 후보     K에서 벡터 + 단어(BM25) 검색 상위 20, 권한 태그로 먼저 거름
 │ 3 재순위   로컬 재순위 모델(cross-encoder)로 질문-후보 관련성 다시 채점
 │ 4 하한     항목 ID별로 묶어 최고 점수, K 하한 미만 버림
 │ 5 우선순위 확정 > 승인 대기 > 미결 > 할 일  (같은 사안이면 지금 상태 하나로)
 │ 6 채우기   원장·원문·회의 표에서 코드가 근거 블록 작성, 권한 재확인
 │ 7 답       LLM 한두 문장 + 값 대조 + 라벨
 ↓
 K에 없으면 → U(발언)에서 하한 이상 → "논의만 있음 · 확인 필요"
 U에도 없으면 → "찾지 못함"
```

- 5단계가 "결정을 우선으로 찾기"다. 관련성(점수)을 먼저 통과한 것들 안에서만 결정을 앞세우므로, 관계없는 결정이 관련 있는 미결을 밀어내지 않는다.
- 6단계에서 권한을 한 번 더 본다. 메타데이터가 낡아 있어도 새지 않게 하는 이중 장치다.

### 4.5 하한 정하기와 평가

- 평가셋: 질문 → 찾아야 할 항목 ID (정답), 그리고 **함정**(논의한 적 없는 주제, 비슷하지만 다른 사안, 권한 밖 정보를 묻는 질문).
- 지표: Recall@5(찾아야 할 걸 찾았나), MRR(몇 번째에 나왔나), **잘못 붙인 비율**(함정에 무언가를 답한 비율), 권한 누출 0건.
- 하한은 정답과 함정 점수 분포가 갈리는 곳으로 정하되, **평가셋을 나눠** 한쪽으로 정하고 다른 쪽으로 확인한다(지금은 같은 셋으로 정하고 확인한 한계가 있다).
- 데이터·임베딩 모델이 바뀌면 다시 잰다.

### 4.6 색인 동기화

- DB의 사건(`events`)을 받아 색인을 고친다: 승인 → 상태 갱신, 대체 → superseded, 미결이 결정에 연결 → 미결 벡터에 연결 표시, 파기 → 삭제.
- 매일 전체 점검: 모든 벡터의 항목 ID가 DB에 있고 상태가 같은지, 건수가 맞는지. 다르면 해당 항목 재색인 + 알림.
- 임베딩 모델을 바꿀 때는 새 색인을 옆에 만들고 평가셋으로 비교한 뒤 바꾼다.

### 4.7 규정 대조의 검색

의견·결정 하나에 대해:
1. P에서 문장 유사도로 관련 조항 (하한 이상)
2. 원장에서 같은 주제의 유효 결정 (SQL) + K에서 다른 주제의 아주 비슷한 결정 (두 경로)
3. B에서 같은 주제 조항 + 아주 비슷한 조항
4. 권한표에서 주제·임계값으로 승인 권한자 (SQL, 숫자 비교)

미결 항목은 규정 대조의 기준으로 쓰지 않는다(정해진 게 없으니 충돌도 없다).

## 5. 권한

- 신원은 서버가 확인한다 (사내 SSO). 화면이 보내는 사용자 ID를 믿지 않는다.
- 판단 순서: 팀장 전체 → 참석자 → 회의별 역할 규칙 → 열람 승인(범위·기간, 1회권은 실제로 열 때 소모).
- 적용 지점: 검색(메타데이터 필터) → 근거 채우기(SQL 재확인) → LLM 입력(볼 수 없는 내용 제외, ID만 "열람 권한 없음").
- 일정: 일정마다 공개 범위. 회의와 연결된 일정은 회의 열람 범위를 따른다.
- 모든 열람·승인 기록은 `events`에.

## 6. 운영과 품질

### 6.1 회의 단위 인사이트 (보고서와 주간 요약에)
- 번복: 결정이 N일 안에 대체됨 (같은 사안이 계속 뒤집히는 신호)
- 오래된 미결: 기한 지난 후속 할 일, N주 언급 없음
- 권한 초과 반복: 같은 역할이 권한 밖 결정을 반복
- 할 일 쏠림·기한 초과
- 규정 충돌이 잦은 조항 (규정이 현실과 안 맞는 신호일 수 있음)

### 6.2 드리프트 감시
- 입력: 검색 1위 점수 평균, 새 주제 비율, 용어집에 없는 단어 비율
- 동작: 라벨 비율(확정·확인 필요·미결), 재작성 횟수, 심판 점수, 파싱 실패율, 처리 시간
- 사람: **팀장 반려율과 반려 사유** — 가장 강한 신호
- 정답 자체: 정책 개정 시 옛 조항을 근거로 승인된 결정 → '재검토 필요' 목록
- 기준선을 벗어나면 알림. LangSmith 메타데이터(회의 ID·파이프라인 버전)와 지표 표에 쌓는다.
- 구현: [pipeline_ops.md](pipeline_ops.md) — 기준선 = champion 승격 직후 30건, 판정 기준표는 §3.

### 6.3 사람 피드백 순환
반려 사유(주제 틀림·요약 틀림 등)와 사람이 고친 주제·문장은 `events`에 남고, 주기적으로 평가셋·용어집·주제 예시에 반영한다. 모델을 고치는 게 아니라 **규칙·평가셋·주제 목록을 고친다.**

### 6.4 주제 관리
`topics` 표에 설명과 예시 문장. '비교할 기준 없음'이나 새 주제가 반복되면 "새 주제 제안"으로 관리자 큐에 올리고, 승인되면 주제 목록과 K 색인에 반영.

### 6.5 시험
- 단위: 규칙(확정 표현, 게이트, 판정표, 날짜 해석)
- 계약: MCP 도구 입력·출력, 권한 거부
- 검색: 4.5 평가셋
- 종단: 회의 몇 건 → 기대 보고서·라벨
- 공격형 함정: 새 주제, 근거 없는 숫자, 권한 밖 질문, 프롬프트 주입이 든 전사문

## 7. 구성

```
웹 화면 ── API 서버(FastAPI) ── 질문 그래프 (빠른 경로)
                │
                ├── 작업 큐 ── 정리 워커 (회의 정리 그래프, 일괄)
                │
                └── MCP 데이터 서비스 (HTTP, 인증) ── DB · 색인 · 파일
                          ▲
             다른 에이전트(슬랙 봇·PR 리뷰·Jira)도 같은 도구로
LLM 서버 (로컬 Ollama/vLLM): 분류 소형 · 작성 대형 · 심판 · 재순위 모델
```

- MCP 도구는 읽기와 제안만. 승인·종료·권한 변경은 사람 화면 → API에서만.
- 회의 정리는 비동기(끝나면 알림), 질문은 SQL·K 검색 위주라 수 초 안.
