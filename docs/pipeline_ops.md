# 파이프라인 감시와 버전 관리

무엇을 재고, 언제 경보하고, 어떻게 승격·롤백하는가. 파이프라인 동작(검색·판정·답변)은 바꾸지 않고 기록만 더한다.

| 파일 | 하는 일 |
|---|---|
| `ledger/pipeline_registry.py` | 버전 지문 계산, 레지스트리(`store/pipeline_registry.json`) |
| `ledger/metrics.py` | 요청별 지표 추출·저장(`store/metrics.db`), 사람 신호 버전별 집계 |
| `ledger/monitor.py` | 드리프트 판정(통계), 정책 개정 재검토 목록, 감시 보고서 |
| `ledger/monitor_api.py` | `GET /admin/monitor`, 서버 시작 등록·요청 기록 연결부 |
| `scripts/drift_report.py` | 터미널 보고서 (경보 있으면 종료 코드 1) |
| `scripts/promote.py` | 기준 평가 → champion 비교 → 승격·거부, 롤백 |
| 관리자 콘솔 '품질 감시' 탭 | 판정표·버전 목록·정책 개정 표시 |

## 1. 파이프라인 버전

같은 질문에 다른 답을 낼 수 있는 것이 바뀌면 다른 버전이다.

| 구성 요소 | 재는 방법 | 바뀌는 예 |
|---|---|---|
| 모델 | 분류(fast)·작성(quality) 모델 이름 | qwen3:8b → 다른 모델, 모델 조합(PRESETS) |
| 프롬프트 지문 | LLM 호출(`.json`·`.text`)의 시스템 문구·출력 형식, MCP Prompt 본문을 AST로 뽑아 키(`파일:함수#순번`)별 해시 | 판정 지시문 한 줄 수정 |
| 임계값 | `ledger/thresholds.py` 숫자 상수 | `MIN_TOPIC_SCORE` 0.50 → 0.52 |
| 주제·별칭 지문 | `topics.json`, `용어집.md`, `data/project/**/*alias*` 파일 해시 | 주제 추가, 별칭 추가 |
| 코드 지문 | 동작 코드 14개 파일의 AST (docstring·주석 제외) | 게이트 규칙 수정 |

- 버전 ID = 위 다섯을 합친 해시 (`pv-` + 10자리). git 커밋은 ID에 넣지 않고 기록으로만 둔다. 문서·주석만 고친 커밋마다 재평가하지 않기 위해서다.
- 감시·관리 코드(metrics, monitor, access, 화면)는 코드 지문에 넣지 않는다.
- 상태: `champion`(운영 기준, 하나) / `challenger`(등록됐지만 승격 전) / `retired`(내려간 이전 champion, 롤백 대상).
- 서버 시작 때 지금 버전을 계산해 없으면 challenger로 등록한다. 회의 기록 저장(`meetings.pipeline_version`)과 요청 지표에 이 ID를 쓴다.

## 2. 요청별 지표

`/chat/stream`·`/chat`이 끝날 때, `scripts/process_meetings.py`가 회의 하나를 정리할 때 1행씩 쌓는다 (`requests` 표). 그래프 최종 상태에서 읽기만 한다.

| 칸 | 출처 | 뜻 |
|---|---|---|
| version, model, source, mode, user | 서버 | 어느 버전·조합에서 무슨 요청이었나 |
| labels | 질의: `answer_label`, 회의·의견: 항목 라벨, 미결 수 | 확정·승인 대기·미결·확인 필요·찾지 못함 건수 |
| check_kinds | 라벨 이유·확인 필요 사유 | 판정 실패·조회 실패·규정 충돌·권한 초과·기존 결정과 다름·기준 문서와 다름·주제 불확실·비슷한 다른 결정·고른 결정 불일치·기타 |
| top1 | research의 주제 자료·정책·기준 문서·원문·다른 주제 결정 점수 | 항목별 검색 1위 점수 |
| below_floor | research | 찾은 기준 없음 또는 주제 자료와 멂(하한 미달) |
| no_topic | 항목 topic | 주제를 못 붙인 항목(새 주제) |
| oov_ratio | 질문 문장·회의 발언 | 주제 목록·용어집·별칭에 없는 낱말 비율 (대략값, 변화만 본다) |
| full_read | `FullReadFallback` 이벤트 | 전체 읽기 대비책 사용 (이벤트가 생기면 센다) |
| parse_errors | usage (`parse_error` 표시를 센다) | JSON 파싱 실패 |
| rewrites, judge_min | `Validation` 이벤트 | 재작성 횟수, 마지막 심판 점수 중 최저 |
| seconds, llm_calls, tokens | 서버 시계, usage | 응답 시간, 호출·토큰 |
| cached, error | 서버 | 저장된 답 재사용, 실행 오류 |
| node_ms | 서버 스트림 (앞 노드가 끝난 뒤부터 이 노드가 끝날 때까지) | 노드별 지연. 보고서·화면에 최근 창의 중앙값·최대 |

LangSmith 추적에도 실행 설정 메타데이터로 `pipeline_version`·`model_preset`을 붙인다. 승격 평가 결과(`store/eval_runs/*.json`)에는 버전·커밋·미커밋 여부·명령·시각을 `meta`로 붙인다.

사람 신호는 이미 `events`에 있다 — `decision_approved`·`decision_rejected`·`decision_edited`·`item_closed`. 결정이 어느 버전에서 나왔는지는 원장에 올린 요청의 버전(`decision_versions` 표)을 먼저 보고, 없으면 그 회의를 정리한 버전(`meetings.pipeline_version`)을 쓴다.

## 3. 드리프트 감지

기준선 창 = champion이 승격된 직후 30건, 최근 창 = 지금 돌고 있는 버전의 마지막 30건 (겹치지 않게). 지금 버전이 champion이 아니면 champion 기준선과 비교한다. 창마다 10건(사람 신호는 결정 5건)이 안 되면 '부족'으로 두고 판정하지 않는다. 저장된 답을 돌려준 요청은 뺀다.

| 묶음 | 지표 | 검정 | 경보 | 주의 |
|---|---|---|---|---|
| 입력 | 검색 1위 점수 분포 | KS 검정 + PSI(0.40~0.80 촘촘한 구간) | PSI ≥ 0.25, p < 0.01 | PSI ≥ 0.10, p < 0.05 |
| 입력 | 새 주제 비율, 검색 하한 미달 비율 | 두 비율 χ² | 차이 ≥ 10%p, p < 0.01 | 차이 ≥ 10%p, p < 0.05 |
| 입력 | 용어집·별칭에 없는 낱말 비율 | 평균 차이 | ≥ 20%p | ≥ 10%p |
| 동작 | 라벨 분포 | 2×k χ² + PSI | PSI ≥ 0.10, p < 0.01 | PSI ≥ 0.10, p < 0.05 |
| 동작 | 확인 필요 비율, 재작성 발생 비율(질의), 심판 저점(≤3) 비율, 전체 읽기 대비책 비율 | 두 비율 χ² | 차이 ≥ 10%p, p < 0.01 | p < 0.05 |
| 동작 | JSON 파싱 실패율(호출당) | 두 비율 χ² | 차이 ≥ 2%p, p < 0.01 | p < 0.05 |
| 동작 | 오류율 | 두 비율 χ² | 차이 ≥ 5%p, p < 0.01 | p < 0.05 |
| 동작 | 응답 시간 (모드별 중앙값) | 비율 | ≥ 1.30배 | ≥ 1.15배 |
| 사람 | 반려율 = 반려/(승인+반려), 승인 전 수정률 | 두 비율 χ² | 차이 ≥ 10%p, p < 0.05 | p < 0.20 |

- 지표가 열네 개라 0.05 하나로 경보를 내면 안정된 창에서도 자주 울린다. 테스트의 가짜 분포 생성기로 같은 분포 30건 창 200쌍을 비교해 보니 경보 문턱 0.01에서 한 번이라도 경보가 난 비율이 2.5%였다.
- 사람 신호는 건수가 적지만 사람이 직접 고친 것이라 가장 강한 신호다. 문턱을 0.05·0.20으로 낮췄다.
- 응답 시간은 모드별로 본다. 회의(60초)와 질의(20초)를 섞으면 요청 구성만 바뀌어도 시간이 바뀐 것처럼 보인다.
- 기준값은 `ledger/monitor.py`의 `RULES` 한곳에 있다. 고치면 이 표도 고친다.

### 정책 개정 감지

레지스트리에 마지막으로 확인한 정책 버전(`policy_seen`)을 둔다. 원장의 현행 정책 버전과 다르면 경보 1건으로 세고, `policy_revision_review(옛, 새)`가 다시 볼 결정을 낸다.

- 대상: 새 버전 시행일 전에 승인된 유효 결정 (그 뒤 승인은 새 정책으로 판정받았다)
- 근거로 삼았다고 보는 기록: 바뀐 조항(개정·신설·삭제)과 같은 주제(권한표 주제 포함), 결정 문장·사유·승인자·부가 정보에 조항 ID, 회의 기록 판정(충돌·변경·예외·안내)에 조항 ID나 그 조항의 예외 ID
- 결과는 '재검토 필요' 목록. 확인했으면 `promote.py --ack-policy`로 지금 버전을 본 것으로 표시한다.
- 시드 데이터(v2 → v3)에서는 CSB-0004(실시간 전송, ARC-02 신설 전 승인)가 나온다.

## 4. 승격·롤백

```bash
.venv/bin/python scripts/promote.py --status             # 버전 목록
.venv/bin/python scripts/promote.py                      # 지금 버전 평가 → 비교 → 승격 또는 거부
.venv/bin/python scripts/promote.py --dry-run            # 평가·비교만
.venv/bin/python scripts/promote.py --rollback           # 이전 champion으로, 복원 방법 안내
.venv/bin/python scripts/promote.py --rollback --apply   # 임계값까지 파일에 복원
```

1. 지금 구성으로 버전을 계산해 등록(없으면 challenger).
2. 기준 평가를 돌린다. 지금은 `eval/run_eval.py --only after`. 결과 파일(`eval/results.*`)은 끝나면 원래대로 돌려놓고, 이번 결과는 `store/eval_runs/`에 남긴다. 다른 평가가 돌고 있으면(`pgrep run_eval|reliability/run.py|process_meetings|list_scaling`) 시간 지표가 흐려지므로 멈춘다.
3. champion의 같은 러너 평가와 비교한다. champion이 없으면 저장소에 커밋된 기준 결과(HEAD의 `eval/results.json` After 열)와 비교한다.
   - 판정 지표(`(%)`는 높을수록, `(건)`은 낮을수록 좋음)가 하나라도 떨어지면 거부
   - 시간 지표가 +30% 넘게 늘면 경고 (거부하지 않음)
   - 호출 수·토큰·비용은 참고
4. 통과하면 champion 교체. 이전 champion은 retired로 남고 승격 이력(lineage)에 쌓인다.
5. 롤백은 lineage를 하나 되돌린다. 지금 파일과 대상 버전을 비교해 임계값(`--apply`면 파일에 복원), 모델 설정, 프롬프트·주제 목록·코드 차이를 알려 주고, 코드는 `git diff/checkout <기준 커밋> -- 파일` 명령만 보여 준다. git은 자동으로 건드리지 않는다.

### 러너 바꿔 끼우기

신뢰도 데이터셋(`eval/reliability/`)이 합쳐지면 `--runner reliability`(`eval/reliability/run.py --split dev`)로 바꾼다. 결과 파일은 `{"scores": {방식: {지표: 값}}}`, `{"scores": {지표: 값}}`, `{지표: 값}` 어느 형식이든 읽는다. 지표 이름은 `(%)`·`(건)`·`시간` 또는 `_rate`·`_count`·`_sec` 꼴이어야 방향을 안다. 결과 파일 경로가 다르면 `RUNNERS`나 `--eval-result`로 맞춘다. 러너가 바뀌면 champion의 같은 러너 평가가 없으므로 한 번은 `--dry-run`으로 재고, 기준 결과를 커밋한 뒤 승격한다.

### 그림자 실행 (설계만)

challenger를 실제 요청 일부에 백그라운드로 돌려 champion 답과 비교하는 방식. 지금은 만들지 않았다.

- 같은 맥북 Ollama 하나를 여러 작업이 나눠 써서, 그림자 실행이 곧 사용자 응답 시간을 늘린다
- 회의 정리는 원장에 승인 대기를 올리고 회의 기록을 저장하는 부작용이 있다. 그림자 실행은 `propose_to_ledger=False`와 별도 기록 저장소(LEDGER_STORE 사본)가 있어야 한다
- 만든다면: 질의·의견만 대상으로, 요청 10%를 샘플링해 서버가 응답한 뒤 큐에 넣고, 유휴 시간에 challenger 그래프로 돌린다. 비교는 라벨 일치·근거 결정 ID 일치·판정 상태 일치 세 가지로 하고 `shadow` 표에 버전 쌍별 일치율을 남긴다. 일치율이 기준선보다 낮으면 승격 전 사람 검토

## 5. 입항 시각 예측 프로젝트와의 대응

| 입항 시각 예측 (port-berth-model) | 이 프로젝트 |
|---|---|
| MLflow 레지스트리 Production / Staging / 이전 버전 | champion / challenger / retired (`store/pipeline_registry.json`) |
| 모델 버전 = 학습 데이터·하이퍼파라미터·가중치 | 버전 = 모델 이름·프롬프트·임계값·주제·별칭·코드 지문 |
| 피처 분포 변화 (최근 입항 패턴) | 입력 드리프트: 검색 1위 점수, 새 주제 비율, 낯선 낱말 비율 |
| 예측 분포 변화 | 동작 드리프트: 라벨 분포, 확인 필요 비율 |
| 최근 21척 MAE (정답이 늦게 도착) | 사람 신호: 반려율·수정률 (팀장 판단이 늦게 도착하는 정답) |
| 터미널 예정보다 나빠지면 드리프트 (relative) | champion 기준선보다 나빠지면 경보 |
| 재학습 (최근 28일 fine-tune, 자동) | 프롬프트·별칭·임계값 수정 (사람이 실패 사례를 보고 고침) |
| 모델 구조 교체 (scratch 학습) | LLM 교체 (qwen3:8b → 다른 모델), 그래프 코드 수정 |
| 배포 게이트: 새 MAE ≤ 운영 MAE | 승격 게이트: 판정 지표 하나도 떨어지지 않음 |
| 게이트 통과해도 Staging까지, 승격은 관리자 버튼 | 등록은 자동(challenger), 승격은 사람이 `promote.py` 실행 |
| 되돌리기 (이전 버전을 다시 Production) | `promote.py --rollback` (임계값 복원, 코드는 커밋 안내) |
| 폴백: 모델이 나쁘면 터미널 예정으로 물러남 | 판단을 미룸: 기준이 애매하면 '확인 필요'로 사람에게, 답 검증 실패면 원장 기록으로 답함 |
| 서버 오류·지연은 드리프트가 아니라 장애 | 오류율·응답 시간은 동작 지표에 두되 따로 표시 (요청 기준 지표라서) |

다른 점: 입항 시각은 정답(실제 접안 시각)이 며칠 뒤 자동으로 오지만, 여기서는 정답이 사람 승인·반려로만 온다. 그래서 자동 재학습이 없고, 고치는 대상이 가중치가 아니라 규칙·지시문·주제 목록이다. 평가셋도 사람이 만든 정답(`eval/ground_truth.json`, 신뢰도 데이터셋)이다.

## 6. 한계

- 낯선 낱말 비율은 조사·어미를 처리하지 않는 대략값이다. 절대값보다 창 사이 변화를 본다.
- 창이 30건이라 작은 변화(10%p 미만)는 잡지 못한다. 요청이 적은 시연 환경에서는 대부분 '부족'으로 나온다.
- 정책 개정 '근거로 삼았다'는 기록 기반이다. 회의 판정이 남지 않은 시드 결정은 주제 일치로만 잡는다.
- 레지스트리는 JSON 파일 하나다. 서버 여러 대가 동시에 쓰면 SQLite 표로 옮긴다.
